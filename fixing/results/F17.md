# F17 — Close the dev schema drift (ISS-025)

**Status:** DONE
**Fixes:** ISS-025 (HIGH — the dev DB was missing `form_submissions.encrypted_at` / `expires_at`)
**Risk taken:** 🟢 — two nullable columns + one index, by the documented upgrade path
**Schema (rule X4):** `database/upgrades/008_form_submission_retention.sql`. schema.sql and the
Drizzle schema already declare the columns (they were never the drifted side) — the drift WAS the
gap between them and the live dev DB.
**Gate:** `forms` + `jobs` in the consolidated final gate (`F16/gate-final.txt`)
**Data left behind:** none — and the two columns are now PERMANENT, which is the point

---

## 1. The drift, reproduced before touching anything

The live dev `taskmanagement` predates migration 0005 and was never upgraded. A fresh `db:setup`
**has** the columns (P41 proved it — schema.sql folded them in), and `taskmanagement_qa` was
provisioned fresh so it has them too: the before-state capture shows exactly that asymmetry —
dev **0/2**, QA 2/2. Production provisioned from schema.sql is fine.

All three failure surfaces the issue records, reproduced live (`before.txt`, exit 0):

```
GET /forms/:id/submissions   -> 500  "Unknown column 'encrypted_at'"
PUBLIC form intake           -> 500  (FormsService writes encryptedAt on submit)
form-submission-expiry job   -> {"ok":false,"error":"Unknown column 'form_submissions.expires_at'…"}
```

The whole Forms feature — the workspace's public intake surface — is unusable on a drifted box.

## 2. The fix — `008_form_submission_retention.sql`

Adds `encrypted_at`, `expires_at` and `idx_form_submissions_expires_at` (the retention job scans
`expires_at < now`; schema.sql ships the index, so upgraded databases get it too). MySQL 8 has no
`ADD COLUMN IF NOT EXISTS` — that is MariaDB syntax — so each ALTER is gated on
`information_schema` via a prepared statement. **Applied twice to prove idempotency: 16/16 both
times.**

**The backfill's one judgement call, stated:** rows written while the columns were absent were
stored *unencrypted* with no retention stamp. `encrypted_at` stays NULL for them — it records when a
row was encrypted, and back-dating it would hide which rows predate encryption. But every PII row
must age out, so legacy rows get `expires_at = submitted_at + 90 days`, the same clock they would
have received at submission time.

## 3. After (`after.txt`, exit 0)

```
GET /forms/:id/submissions   -> 200, and the list shows the row
public intake                -> 201; the stored row has encrypted_at set and
                                expires_at = submitted_at + exactly 90 days
form-submission-expiry job   -> {"ok":true, …}
```

## 4. Rule X9's first half is RETIRED — and the old probes were defused

The drift was deliberately kept reproducible while earlier phases needed it: the F7, F8 and F15
probes each ADDed the two columns for their public-form scenario and DROPped them again. From 008
on, the columns are present **on purpose, everywhere** — so those probes' cleanup DROPs would now
*reintroduce* the drift on every re-run. All three evidence scripts had their DROP lines neutralized
in this phase (a comment marks why). Zero `DROP COLUMN encrypted_at/expires_at` lines remain
anywhere under `fixing/evidence/`.

With F15 having dropped the stale triggers, **both X9 states are now closed** — nothing in the dev
database is deliberately broken any more.
