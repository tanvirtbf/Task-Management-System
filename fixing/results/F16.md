# F16 — Orphans and cascades (ISS-073 · ISS-022 · ISS-041)

**Status:** DONE

**Risk taken:** 🟡 — one new table, three new write-path steps inside existing transactions
**Schema (rule X4):** `database/upgrades/007_orphans_and_cascades.sql` + `database/schema.sql` +

**Gate:** the consolidated final gate (`gate-final.txt` — see §5 for why there are two gate files)
**Data left behind:** none — baseline re-verified, the purge queue empty

## 1. ISS-073 — notifications went with nothing

`notifications.entity_id` is polymorphic, so no FK is possible — it was the **only** child table
that orphaned (P37: 23 of 24 relationships clean). Hard-delete a task and its notifications stayed
in every recipient's inbox forever, navigating to a 404. Thirteen had already accumulated in dev
before anyone looked.

**The change.** `NotificationsRepo.deleteByEntity("task", subtree)` inside the hard-delete
transaction — the whole subtree, because the FK cascade takes descendants and their notifications
have no FK to follow either. `007` also sweeps any orphans that pre-date the fix (idempotent; 0 on
the current demo DB, but QA/prod may differ).

## 2. ISS-022 — R2 bytes stranded forever

The attachments FK is `ON DELETE CASCADE`, so a hard delete removes the **rows** instantly — and the
r2-purge job finds objects *by reading soft-deleted rows*, which have just vanished. The bytes
stayed in the bucket permanently: P4 proved it with four stranded objects deleted by hand.

**The change.** A new `r2_purge_queue` table. The hard-delete transaction copies the subtree's
storage keys (main + thumbnail) into it **before** the task row goes — same transaction, so either
the task is deleted with its keys queued, or nothing happens; the window in which bytes could orphan
does not exist. The r2-purge job drains the queue on its normal schedule, objects-first-row-second
(same crash-safe contract it already had), and its dry run reports `wouldDrainQueue`. **Soft-deleted
attachments are queued too** — their rows also cascade, before the ordinary 7-day purge would have
reached them. No grace period applies: the task is already permanently gone, so its files are too.

Proof, with real R2 traffic (`f16-probe.txt`):

```
parent + child, 3 uploads (1 already soft-deleted)
hard delete parent          -> 204, attachment rows cascade (as before)
r2_purge_queue              -> ALL 3 keys, incl. the child's and the trashed one
job dry_run                 -> wouldDrainQueue: 3, queue untouched
job real                    -> queueDrained: 3, r2Errors: 0, queue empty
```

## 3. ISS-041 — the space that came back empty

Archive cascades one level (lists); unarchive cascaded **not at all**. P8 archived Marketing for two
seconds and its three boards were invisible for ninety minutes. The code's own comment argued
restoring was impossible without wrongly resurrecting independently-archived lists.

**That concern is real, and the discriminator already existed.** The archive cascade stamps every
list with the **same instant** the space gets, and it skips lists that were already archived — so
those keep their earlier timestamp. Restoring `archived_at = <the space's archivedAt>` is the exact
inverse: `ListsRepo.unarchiveBySpaceArchivedAt`, called inside the unarchive transaction *before*
the space's stamp is cleared (the equality needs it). The audit row now carries `lists_restored`.

The discriminating case, proven:

```
archive L1 individually        (its own timestamp)
archive the space              (cascade takes L2 with the space's timestamp)
unarchive the space
  -> L2 is BACK                (was: space came back empty)
  -> L1 STAYS archived         (independently archived — untouched)
  -> audit context: lists_restored: 1
```

*Known narrow edge, recorded:* `archived_at` is second-precision TIMESTAMP, so a list archived
independently in the **same second** as the space-archive would match the equality and be restored
with it. Sub-second, harmless, and fixing it would need a schema column — out of proportion.

## 4. The P37 orphan sweep — the phase's acceptance bar

All 24 queries re-run on the final tree: **24 of 24 clean** (P37 scored 23). The one dirty

## 5. Two gate files, and why

The first gate run (`gate.txt`) was launched and then F18's edits landed mid-run in the same
working tree. ts-jest compiles per-file at require time, so its `spaces`/`lists` rows measured a
broken intermediate state (`lists` 171/171 failed = the mass-fail signature, not 171 real bugs).
Those rows are **void** — the run taught nothing about the product. `gate-final.txt` is the
consolidated 8-module gate on the settled tree and is the one this phase (and F17/F18) stands on.
The straddle rule was already written down after F3; this is what ignoring it for an hour looks
like, kept as a worked example.
