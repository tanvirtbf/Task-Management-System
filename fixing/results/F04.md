## 1. Why this phase shrank to a verification

P30 measured ISS-081 as two halves: every stored SLA deadline was **360 minutes short** (an S0 was
born already breached at −240 min), and the breach endpoint was blind for the **first six hours** of
every breach, then under-reported `minutes_breached` by 360 — while `v_breached_sla` disagreed with
it across that whole window.

None of that was SLA code. All of it was ISS-001 wearing §29's clothes: `computeSlaDueAt` computed
the right instants and `SlaRepo` compared them correctly against `UTC_TIMESTAMP()` — the *storage*
was six hours off underneath both. F3 fixed the storage, so the original F4 to-do list (switch
`SlaRepo` to `NOW()`, re-derive the views) became wrong or already-done:

- ~~`SlaRepo.ts:95` → `NOW()`~~ — **rejected.** Under the UTC session `NOW()` and `UTC_TIMESTAMP()`
  are identical; keeping `UTC_TIMESTAMP()` stays correct under *any* session zone.
- ~~re-derive `v_breached_sla` / `v_current_on_call`~~ — done in F3
  (`database/upgrades/005_clock_views.sql`, applied to both DBs).

What remained was the plan's own instruction: *re-run the P30 sweep once, as an independent
confirmation rather than a fix.* That is this phase.

## 3. Two small observations (neither is a defect introduced here)

- **`?limit=1` is silently ignored** by `GET /sla/breached` — there is no `limit` handling anywhere
  in the §29 validator/service/repo. P30's "?limit=1 → 200" only ever asserted the status code, so
  this is not a regression and not newly filed: the endpoint returns a bare, unpaginated array by
  spec, and unknown query params are ignored API-wide. Recorded so nobody reads P30's PASS line as
  "limit works".
- **`POST /eng/report-bug` requires `reporter_team`** (enum: ops/cs/inventory/listing/marketing/
  internal). Matches the §22 validator by design; noted because the first sweep draft tripped on it.
