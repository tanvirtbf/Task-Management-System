# F11 — Load shedding instead of 500s (ISS-087)

**Status:** DONE
**Fixes:** ISS-087 (HIGH — 50 concurrent requests, 37 failed with generic 500s)
**Risk taken:** 🟡 — a pool-config change plus one new error branch; no query or business logic touched
**Gate:** the repo's own red test (`users` → *"serves 50 parallel reads"*) is the acceptance
criterion · the P40 ramp re-run against the 5 000-task perf DB
**Data left behind:** the perf scratch DB gained its RBAC bootstrap (see §4) — the demo DB untouched

---

## 1. Reproduced first, on the real fixture

`fixing/evidence/F11/ramp-before.txt` — 5 000-task workspace, the endpoint with the largest
per-request fan-out (`GET /lists/:id/tasks?limit=50`: 1 list lookup + 2 page/count + 4 hydration =
**7 queries, peak 4 simultaneous acquires**):

```
conc  ok   failed   statuses                p50    max
 5     5     0      200×5                   303    312
10    10     0      200×10                  302    328
15    15     0      200×15                  322    363
20    20     0      200×20                  462    504
30     6    24      200×6  500 internal×24  505    537     <-- collapses
50    20    30      200×20 500 internal×30  560    849
50 seq 50    0      (the P40 control)                      <-- sequential is fine
```

Identical shape to P40's measurement. The cliff is between 20 and 30 because a *request* is not a
*query*: ~30 in-flight requests want ~120 acquires against 20 connections + 50 queue slots, and
mysql2 throws `Queue limit reached` on the next one.

## 2. The fix — two parts, and one deliberate non-change

**`DB_POOL_QUEUE_LIMIT: 50 → 0` (unlimited wait queue).** A burst becomes *latency* instead of
*failure*. `.env.example` already shipped `0`; only the deployed `.env` had `50`, so this was a
configuration defect, not a code one. `DB_POOL_MAX` stays at **20** on purpose — MySQL's
`max_connections` is 151 and the box hosts five other production apps, so raising the pool just
moves the wall and takes the neighbours down with it. Both facts are now written into `.env` itself,
where the next person will change the value.

**Pool exhaustion → 503 + `Retry-After`, never a generic 500.** `errorHandler` gained a branch
before the unknown-error fallback: mysql2's `Queue limit reached` (plus `ER_CON_COUNT_ERROR` and the
`PROTOCOL_ENQUEUE_AFTER_*` family a closing pool raises) now renders
`503 service.unavailable` with `Retry-After: 2`, logged at **warn** — capacity pressure is a load
signal, and paging on it as a server error is exactly the monitoring pollution the issue describes.

**Not done: reducing the hydration fan-out.** The plan listed it; the measurement says it is not
needed and would cost something. The four hydration reads run in one `Promise.all`; serialising them
would cut peak acquires from 4 to 1 but add three round-trips of latency to *every* request, and the
unlimited queue already absorbs the peak (50 concurrent: **0 failed**, p50 797 ms). Optimising a
path with no demonstrated failure would be exactly the "fix the neighbourhood" rule X5 forbids.
Recorded here so the option is visible if a future load profile changes the answer.

## 3. Proof

**The ramp, after** (`ramp-after.txt`, exit 0) — same fixture, same endpoint:

```
conc  ok   failed   p50    max
 5     5     0      343    357
10    10     0      350    378
15    15     0      358    404
20    20     0      414    503
30    30     0      545    649      <-- was 24 failed
50    50     0      797   1057      <-- was 30 failed
50 seq 50    0                      control still clean
```

Every level fully served. The extra latency at 50 is the queue doing its job.

**The 503 path, proven rather than assumed** (`shed-503.txt`). With the unlimited queue the branch
can never fire in the deployed config, so it was exercised against a deliberately tiny pool
(`DB_POOL_MAX=2`, `DB_POOL_QUEUE_LIMIT=1`), 40 concurrent:

```
40 × 503 service.unavailable
Retry-After: 2
"The server is busy. Please retry in a moment."
ZERO generic 500s
```

**The repo's own acceptance test.** `tests/users/list.test.ts` → *"serves 50 parallel reads with
identical, consistent results"* had been red since at least 2026-07-30, and it was the last
remaining failure in **both** affected modules:

```
users    278/279  ->  279/279
tasks    358/359  ->  359/359
```

**No known failing server test remains.** That single red line — the one ISS-087 filed, and the one
ISS-093 mis-identified back in F3 — is gone.

(The gate chain reported 2 failures for `tasks`; run solo it is 359/359. Both are the concurrency
tests, so they are load-sensitive by construction — running them while another module's pool is
still draining is the very condition this phase is about. Recorded rather than glossed; see
`gate.txt`.)

## 4. The perf fixture needed a bootstrap first (recorded, not hidden)

`taskmanagement_perf` was built before dynamic RBAC and had **zero `roles` / `user_roles` rows**.
After F7, its users hold nothing, so the first ramp attempt returned `404 list.not_found` at every
level — the visibility layer, not the pool. A load test against that state would have measured the
404 path and "passed" meaninglessly. `bootstrap-perf.ts` runs the same `bootstrapRbac` a real
workspace gets (56 permissions, 4 roles, 40 workspace grants, 40 space grants); the API must be
restarted afterwards because `PolicyService` caches actors by permissions-version.

Worth keeping in mind for F30, which also uses this fixture.
