## 1. One bug, three times

All three counters drift for the same reason: each is maintained by a rule that does not match how
the application actually writes.

| counter | the rule | how the app actually writes |
|---|---|---|
| `comments_count` | AFTER **DELETE** trigger | the API **soft**-deletes (stamps `deleted_at`) |
| `forms.submission_count` | INSERT-only trigger | the retention job **DELETEs** rows |
| `subtasks_count` / `_completed` | *nothing at all* | — |

`attachments_count` is the one that gets it right — an AFTER UPDATE trigger that moves in **both**
directions and understands soft delete — and it is the model copied here.

## 2. ISS-065 — `comments_count`

`trg_comments_after_delete` can only fire if someone removes a row by hand. New:
`trg_comments_after_update`, shaped exactly like the attachments one — a comment counts while
`deleted_at IS NULL`, so the counter moves on the crossing in either direction and **ignores an
ordinary edit**.

```
3 comments                        counter 3   live rows 3
delete one (204)                  counter 2   live rows 2      (was STUCK at 3)
the list a reader sees            2 non-tombstone rows — the badge matches
edit a comment                    counter 2                    (an edit must not move it)
restore the deleted one           counter 3                    (moves back up too)
```

## 3. ISS-080 — `forms.submission_count`

`trg_form_submissions_after_delete` added. Proven against **the real retention job**, not a hand
DELETE: age one submission past retention, `POST /jobs/form-submission-expiry`, and the count
follows the rows from 3 to 2.

## 4. ISS-046 — the subtask counters, and the crash that was waiting

These cannot be triggers. MySQL forbids a trigger on `tasks` from modifying `tasks`, which is why
the original `trg_subtasks_after_*` triggers were removed — `schema.sql:1482-1488` records the
decision and says the maintenance must be app-side.

**`TasksRepo.recomputeSubtaskCounters(parentId)` — recompute, not increment.** The other two bugs in
this phase were both increment-only rules that drifted the moment a write happened by a path their
author had not pictured. An absolute recompute cannot drift: whatever a caller misses, the next call
repairs. It is one indexed UPDATE on a path already inside a transaction. Called from six places:
create-with-parent, status change, archive, unarchive, hard delete, and bulk (**one recompute per
DISTINCT parent** — a bulk of 50 siblings is one call, not fifty).

"Counts" = a live, non-archived child, matching what `GET /tasks/:id/subtasks` returns, so the badge
and the list agree by construction.

```
2 children                     2/0     (was 0/0 — every task in production reports 0/0)
mark one done                  2/1
move it back to open           2/0     (both directions)
archive a child                1/0     …and the subtask LIST also returns 1
unarchive                      2/0
BULK both to done              2/2
hard-delete a child            1/1
```

### 4a. SCAN-H4 — the stale triggers, reproduced first-hand and then removed

The first run of the new maintenance turned **every subtask status change and every hard delete into
a 500**:

```
ER_CANT_UPDATE_USED_TABLE_IN_SF_OR_TRG — Can't update table 'tasks' in stored
function/trigger because it is already used by the statement which invoked it
```

That is SCAN-H4: the dev database still carried `trg_subtasks_after_insert/update/delete`, which
exist **nowhere else** — not in `schema.sql`, not in a freshly provisioned DB, not in the QA
database, not in production. They were preserved deliberately (fixing rule X9) so this phase could
confirm the crash rather than take it on faith, and it did — this fix could not have shipped without
tripping over them.

```
before   taskmanagement 12 triggers   taskmanagement_qa 9    <- the 3 extra are the stale ones
after    taskmanagement 11 triggers   taskmanagement_qa 11   <- both now carry F15's 2 new ones
```

`006_counters.sql` drops all three, as step 0.

### 4b. A MySQL restriction I hit twice, worth writing down

The backfill and the repo method were both first written as correlated subqueries
(`UPDATE tasks … (SELECT … FROM tasks …)`) and both failed with **error 1093, "You can't specify
target table for update in FROM clause"** — the same family of restriction that made the triggers
impossible. Both are now a JOIN against a **derived table**, which MySQL materialises first and
therefore permits. The upgrade script says so inline, because the next person will write the
subquery version first too.

## 5. The backfill, and one thing to expect

`006_counters.sql` §3 recomputes all three counters for every existing row — absolute assignments,
so re-applying the script is a no-op (verified: applied twice, 10/10 both times).

> **A badge will appear on task cards for the first time.** `BoardCard.tsx:198` renders the subtask
> badge only `if (subtasksCount > 0)`, and that was never true anywhere. The plan flags this; it is
> the fix working, not a regression.

## 6. A note on the runner

`fixing/evidence/F15/apply-upgrade.cjs` — mysql2 does not understand the `DELIMITER $$` directive
the mysql CLI uses for trigger bodies. The first attempt at parsing this file with a whole-file
regex mangled multi-line comment blocks into bogus statements and half-applied the script; the
runner now walks line by line tracking the current delimiter. Reusable for later upgrades.
