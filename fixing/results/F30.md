## 1. ISS-088 — the four filesorts, gone at the plan level

P40's finding: the code paginates by `internal_id` (comments tie-break on it after `created_at`)
while every available index ends in a time/status column — so MySQL found each page by index and
then **sorted it separately, per page, forever**. Nothing was slow at 5,000 tasks, but the sort
cost scales with the result set: it was the first thing that would bend at 10×.

Four covering-order indexes, each matching its query's ACTUAL `ORDER BY` (the plan's note said
`(task_id, internal_id)` for comments — the code orders by `(created_at, internal_id)`, so the
index follows the code, not the note):

```
tasks               idx_tasks_list_internal              (primary_list_id, internal_id)
comments            idx_comments_task_created_internal   (task_id, created_at, internal_id)
task_activity       idx_task_activity_task_internal      (task_id, internal_id)
workspace_activity  idx_workspace_activity_ws_internal   (workspace_id, internal_id)
```

**Before/after on the same 5,000-task / 20,000-comment / 47,000-activity perf fixture**
(`explain-before.txt` / `explain-after.txt`, probe re-runnable):

| query | before | after |
|---|---|---|
| list tasks | `uq_tasks_list_number` + **filesort** | `idx_tasks_list_internal`, no sort |
| task comments | `idx_comments_task_time` + **filesort** | `idx_comments_task_created_internal`, no sort |
| task activity | `idx_task_activity_task_time` + **filesort** | new index, backward scan, no sort |
| workspace activity | time index + **filesort** | new index, backward scan, no sort |

Bonus observed, not claimed as design: `overdue count` left its full-table scan (`ALL`, 4,452 rows
→ `ref`) after the DDL's implicit re-analyze.

**The P40 latency table, re-run** (`latency-probe.cjs`, API on :5713 against the perf DB, median
of 7, compared against P40's recorded medians): **every endpoint 200, none slower** — and the two
list reads show the filesort's cost directly: `?limit=50` 17.3 → 9.9 ms, `?limit=200` 19.6 →
12.0 ms. `latency-after.txt` has the full table.

## 2. ISS-006 — the bundle, split where splitting wins

Baseline (re-measured on today's tree, matching the issue): main **1,450 kB / 448 gz**, drawer
**551 kB / 173 gz**, vite's >500 kB warning.

**The antd experiment — tried, measured, rejected.** Forcing antd + `rc-*` into one `manualChunks`
bucket produced a 1,178 kB chunk that became a *static dependency of the entry*: it eager-loaded
the previously-lazy Table (164 kB) and the drawer's antd pieces, growing first-load gzip from
~448 to ~578 kB. Strictly worse on both of the issue's metrics. Evidence kept:
`build-antd-bucket.txt`.

**What shipped** (`vite.config.ts`, the reasoning in a comment where the next person will look):
package-name-matched buckets for **react** (284 kB / 91 gz), **editor** (tiptap + prosemirror,
375 kB / 120 gz — loads only with the drawer), **icons** (32 kB / 10 gz), **map** (maplibre,
lazy); antd deliberately left to Rollup's per-usage splitting (shell antd in the entry, Table
stays lazy, drawer antd in the drawer chunk). `chunkSizeWarningLimit: 1200` with the measurement
as its justification — a deliberate, cached vendor entry is not the accidental monolith the
heuristic exists to catch.

| | before | after |
|---|---|---|
| entry chunk | 1,450 kB / 448 gz | **1,146 kB / 351 gz** |
| task drawer | 551 kB / 173 gz | **171 kB / 52 gz** + editor 120 gz (parallel, independently cached) |
| first-load gzip (entry+react+icons) | 448 | **452 (+0.7% — split-dictionary cost)** |
| redeploy re-download | 448 gz (one monolith) | **351 gz** (react/icons/editor/map stay cached) |
| build warning | yes | **no** |

First paint is unchanged within noise; the real win for BD network conditions is the repeat-visit
path — weekly app deploys invalidate 351 gz instead of 448, and the editor/react/icons chunks
survive every deploy. Client tsc clean, vitest 44/44.

## 3. ISS-005 — re-measured: the 16.7 s boot no longer exists

The issue recorded `tsx` at **16.7 s** to listening vs 1.2 s compiled (P1, late May). Re-measured
on today's tree with a spawn→first-200-from-`/health` probe (`boot-probe.cjs`, re-runnable, two
runs each):

```
npx tsx src/server.ts   4.1 s   4.1 s
node dist/server.js     2.1 s   1.9 s
```

The 4× regression the issue described is gone — most plausibly tsx/esbuild improvements across
the intervening months plus a warmer module cache; the tree is *bigger* now than when 16.7 s was
recorded. A compiled-dev pipeline to save the remaining ~2 s would add a second dev workflow (and
its staleness traps — this campaign already met one in nodemon) for no felt benefit, so nothing
was built. Closed as **re-measured, does not reproduce at the recorded magnitude**, with the probe
kept for the next time someone suspects boot time.
