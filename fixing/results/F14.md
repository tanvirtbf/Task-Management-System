## 1. ISS-002 — the demo seed's guard defeated itself

`seed-demo.ts` truncates **every table**. It had two guards meant to be independent layers:
`Config.IS_PROD` and `ALLOW_DEMO_SEED=1`. But the npm script was
`cross-env NODE_ENV=dev tsx src/db/seed-demo.ts`, which **overwrites the real environment**, so
`Config.IS_PROD` was permanently false on the documented invocation path. The layer meant to stop a
production run was the one the script disabled — and the file's own comment says *"the npm script's
`cross-env NODE_ENV=dev` is NOT a guard"* immediately before relying on the thing that `cross-env`
defeats.

**The change.** `cross-env` is gone from the script, which restores guard 1. And a **third guard**
was added that does not depend on an environment variable at all — the same idea `db:setup` already
uses with its table count, which P41 proved works. A production database is recognised by its
**data**: any user account the demo seed did not create means this looks like a real workspace.
`ALLOW_DEMO_SEED_OVER_DATA=1` is the deliberate, separate, loud override.

```
NODE_ENV=prod + ALLOW_DEMO_SEED=1   -> exit 1, REFUSING (guard 1, restored)
NODE_ENV=dev  + no ALLOW_DEMO_SEED  -> exit 1, REFUSING (guard 2)
NODE_ENV=dev  + ALLOW_DEMO_SEED=1
              + one non-demo account -> exit 1, "…holds 1 user account(s) that the demo seed did
                                         not create" (guard 3, new)
tasks 46 -> 46   nothing was truncated by any of the three
```

## 2. ISS-079 — `?dry_run` silently meant "delete"

`req.query.dry_run === "true"` — so `?dry_run=1`, `?dry_run=yes`, `?dry_run=TRUE` and a bare
`?dry_run` all evaluated to **false** and ran the job for real. Three of the six jobs delete rows.
This was found the expensive way: a tester typed `?dry_run=1`, believed they had asked for a
preview, and destroyed a row.

The new parse is deliberately **asymmetric**, because a safety control must never disengage
silently:

| input | result |
|---|---|
| `true`, `1`, `yes`, `y`, `on` | dry run |
| a **bare** `?dry_run` | dry run — you typed the word, you meant the preview |
| `false`, `0`, `no`, `n`, `off`, absent | real run |
| anything else | **422**, not a guess |

```
?dry_run=true  200 true     ?dry_run=false  200 false
?dry_run=1     200 true     ?dry_run=0      200 false
?dry_run=yes   200 true     (absent)        200 false
?dry_run=TRUE  200 true     ?dry_run=maybe  422 'unrecognised value "maybe" — use true/false…'
?dry_run=on    200 true
?dry_run       200 true
```

The handler gained a `next` parameter to deliver that 422: Express 4 does not catch an async throw,
so leaving it to bubble would have turned an unparseable value into a crash — a different silent
failure in place of the one being fixed.

## 3. ISS-003 — a server that reported READY and could not log anyone in

`ACCESS_TOKEN_SECRET` was effectively boot-validated (express-jwt refuses to construct).
`REFRESH_TOKEN_SECRET` was not: the process booted, `/health` **and** `/health/ready` both answered
**200 ready**, and then every login returned `500 auth.token_config_missing`. A load balancer or
uptime monitor saw a perfectly healthy instance nobody could sign in to — silent, and invisible to
exactly the thing watching for trouble.

Both secrets are now a hard no-boot, in the same place and the same shape as the existing
`ENCRYPTION_KEY` check:

```
REFRESH_TOKEN_SECRET=""  ->  exit 1
   "REFRESH_TOKEN_SECRET is missing — refusing to boot. Without it the server
    would report READY and fail every login."
   …and it never printed "Listening".
```

## 4. ISS-004 / ISS-090 — config that stops lying

**`COOKIE_SECRET` removed** from `config`, `app.ts`, `.env` and `.env.example`. Nothing in this app
signs a cookie — `bb_refresh` is a plain httpOnly cookie carrying a self-signed JWT, and P1 measured
that booting with `COOKIE_SECRET=""` leaves the full refresh round-trip working. It sat in `.env`
looking mandatory. `SECRET_KEY`, `REDIS_URL` and `CLOUDFLARE_TOKEN_VALUE` went with it — the
SCAN-M8 family, present in the env files and read by `Config` nowhere.

**ISS-090's premise needed a correction, and the fix changed accordingly.** The issue calls the six
`SMTP_*`/`EMAIL_*` keys *"a second, unused mail configuration (the working one is `MAIL_*`)"* and
suggests deleting them. They are not a second configuration: `config/index.ts:120-125` reads them as
the **fallback tier** — `MAIL_HOST ?? SMTP_HOST`, `MAIL_FROM_ADDRESS ?? EMAIL_FROM`, and so on.
Deleting them would remove a working fallback for anyone migrating from those names. They are now
**documented** in `.env.example` as exactly that, commented out. Same for
`OPENAI_MAX_OUTPUT_TOKENS` (code default 800).

The probe then checks the general property rather than the nine names: **every variable `Config`
destructures appears in `.env.example`.** That caught one the issue never listed —
`R2_SIGNED_URL_TTL`, in `.env` and read by `Config` but absent from the example file. **68/68 now
documented.**
