## 1. The instrument

`fixing/evidence/F01/clock-probe.cjs` answers one question per column: **when the application writes
a known instant, does the database hold that instant, and does the API give it back?**

Three independent observations per write:

| observation | how it is taken |
|---|---|
| **asked** | the instant the caller intended (a JS `Date`) |
| **stored** | `CAST(col AS CHAR)` — raw SQL, no driver conversion |
| **wire** | what `GET /tasks/:id` returns to a client |

It reports two drifts — **DB drift** (stored vs asked) and **wire drift** (wire vs stored) — plus the
six settings that must agree, the comment edit window, and the DATE round-trip. It exits **0** only
when every drift is zero, so it works as a pass/fail gate for F2–F5.

It creates only `TEST-F01-*` rows and removes every one before exiting.

```
node fixing/evidence/F01/clock-probe.cjs                       # canonical
API_PORT=5716 node fixing/evidence/F01/clock-probe.cjs         # against another config
node fixing/evidence/F01/clock-probe.cjs --json out.json
```

## 3. What the probe actually shows — two equal and opposite errors

```
tasks.sla_due_at              app     asked 06:19:05   stored 06:19:06    DB -6.00 h   wire +6.00 h
tasks.completed_at            app     asked 06:19:06   stored 06:19:06    DB -6.00 h   wire +6.00 h
tasks.archived_at             app     asked 06:19:06   stored 06:19:06    DB -6.00 h        -
tasks.created_at              MySQL   asked 06:19:06   stored 12:19:06    DB  0.00 h   wire +6.00 h
tasks.updated_at [assign]     app     asked 06:19:07   stored 06:19:08    DB -6.00 h   wire +6.00 h
tasks.updated_at [patch]      MySQL   asked 06:19:08   stored 12:19:08    DB  0.00 h   wire +6.00 h
notifications.snoozed_until   app     asked 11:19:09   stored 11:19:10    DB -6.00 h        -
checklist_items.completed_at  app     asked 06:19:10   stored 06:19:10    DB -6.00 h        -
tasks.due_date (DATE)         app     asked 2026-08-10 stored 2026-08-10  DB  0.00 h   wire  0.00 h
```

- **WRITE** (Drizzle → MySQL) stores **6 hours early** — Drizzle formats the Date as UTC, MySQL reads
  that string as Dhaka.
- **READ** (MySQL → Drizzle) reports **6 hours late** — Drizzle takes the stored Dhaka wall clock and
  labels it `Z`.

**This single pair explains the whole cluster, including why parts of it looked fine during testing:**

| situation | net effect |
|---|---|
| app-written column, read back **through the app** | −6 then +6 = **0**. Looks correct. This is why snooze (P24), the r2-purge window (P23) and session expiry all behaved. |
| app-written column, compared **in SQL** | the stored value is 6 h early but `NOW()` is not → **breaks**. This is exactly **ISS-081**. |
| MySQL-written column, read through the app | stored correctly, +6 on read → **the user sees a time 6 h late**. This is what `created_at` does. |
| **two writers on one column** | they land 6 h apart → **ISS-052** |

The last one is now asserted explicitly:

```
updated_at >= created_at ?   *** NO — created 12:19:08, then ONE assign set
                                 updated_at to 06:19:09 (-6h EARLIER than creation). ISS-052 ***
```

A row that has been updated before it was created is impossible, and the probe fails on it.

## 4. A correction to ISS-058's evidence — the DATE half does not drift

P19 recorded that under `TZ=UTC` with `DB_TIMEZONE=+06:00`, a stored `2026-07-07` comes back as
`2026-07-06`. **That measurement was taken with a raw `mysql2` connection, not through the product's
Drizzle path, and the product does not behave that way.**

Verified at the driver level — the P19 claim is true *for raw mysql2*:

```
driver timezone=undefined -> DATE arrives as Date 2026-07-07T00:00Z -> renders 2026-07-07  OK
driver timezone=+06:00    -> DATE arrives as Date 2026-07-06T18:00Z -> renders 2026-07-06  SHIFTED
```

But Drizzle's `date()` **defaults to `mode: "string"`**, so every DATE column reaches the serializer
as a plain string and `toWireDate`'s date-component branch never executes. Checked on all six DATE
columns under the worst configuration (`TZ=UTC` + `+06:00`):

```
tasks.due_date                  string  safe
tasks.start_date                string  safe
on_call_shifts.week_start       string  safe
on_call_shifts.week_end         string  safe
sprints.start_date              string  safe
department_reports.week_start   string  safe
```

**Consequences:**
- **ISS-058's primary claim is unaffected and still true** — `workspaces.timezone` is read by nothing.
  Only its secondary "and dates shift a day" evidence was a simulation artefact.
- **F2 (the DATE half) collapses to almost nothing.** There is no DATE bug to fix. What remains is
  optional tidying: the date-component branch in `toWireDate` (`taskSerializer.ts:83-90`) and
  `onCallSerializer.ts:27-33` is dead code, and `dateStrings: true` is unnecessary because Drizzle
  already returns strings.
- ISS-058 has been annotated in `testing/ISSUES.md` with this correction rather than silently left
  to mislead the fix.

## 5. The six settings, as they stand today

```
process TZ                Asia/Dhaka            (pm2 sets this in prod)
MySQL session time_zone   SYSTEM  (= Dhaka)     (prod sets +06:00 via DB_TIMEZONE)
MySQL NOW()               12:19:06              = Dhaka wall clock
MySQL UTC_TIMESTAMP()     06:19:06              = NOW() - 6h
node new Date()           06:19:06Z
NOW() vs the node clock   0 h                   AGREE
```

The two clocks **do** agree. Nothing here is misconfigured — which is the point. **ISS-001 is not a
configuration error and cannot be fixed with an environment variable.** It is Drizzle applying a
different frame from the one the session uses, in code.

One difference worth carrying into F3: **dev leaves `DB_TIMEZONE` empty while production sets
`+06:00`**, so dev never runs `SET time_zone` and never sets the driver's `timezone` option. The two
environments therefore have different driver configurations, and F3 must be verified under the
production pair (config 3 above), not just the dev default.
