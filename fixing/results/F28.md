## 1. D12.1 — the Guest role is finally what its name says (ISS-094)

The seeded Guest role held **19 grants at scope=all** — a faithful copy of the pre-RBAC product,
where "guest" was a label and every authenticated user could do everything except upload files.
F7 made all 56 keys real route gates, and the faithfulness became a hole: a guest could delete any
task in the workspace, plan the sprint, edit postmortems, and read every public-form submission
(customer names + phone numbers).

Now **7 grants**: `space.view` · `task.view` · `member.view` · `activity.view` · `comment.create`
· `assistant.use` · `bug.report`. Twelve revoked, **member untouched at 20** — measured in code
(`SYSTEM_ROLE_GRANTS`), in both live DBs (upgrade 011), and on the wire (`/me/permissions` returns
exactly the 7). The role description was part of the fix: it used to *say* "Same as a member today,
except uploading files", which was the defect in prose.

**The F26 workaround is retired:** the Sidebar's Engineering gate dropped its `permRole !== "guest"`
term — the grants alone now produce the right answer, which is what F26's note predicted.

### …and the one write a guest keeps had to be repaired to survive it

The regression gate exposed a real bug in the revocation itself: `bug.report` stayed granted, but
`POST /eng/report-bug`'s mechanism is a task insert, and `TaskWriteService.create` asserts
`task.create` — so the route admitted a guest and the service 403'd. A key that opens no door.

Fix: a **named intake principal** (`rbac/principals.ts` §2b, new `ActorKind: "intake"`), installed
via `runWithPrincipal` around exactly the create call. Same pattern and same narrowing as the
public form: the actor carries only `task.create` inside the Bug Triage list's space, visibility
covers that one list, and attribution (created_by, activity, notifications) stays the real caller —
pinned by a new spec. The bypass lives in the one file `grep elevate` audits, per that file's rule.

## 2. D12.2 — SLA deadlines move to the business clock; the fiscal year leaves (ISS-029)

ISS-029: four workspace settings stored, validated, and read by nothing. Three gained their consumer,
one was removed — both halves are the same honesty fix.

**The clock.** `working_days` + `business_hours_start/end` (+ `timezone`) now drive
`computeSlaDueAt` through new pure helpers in `utils/dhakaTime.ts` (`addBusinessMs`,
`addBusinessDays`). Policy numbers unchanged; the clock they count on changed:

| policy | was (wall clock) | now |
|---|---|---|
| Bug S0 · 2h | +2 hours — 17:30 Thu → **19:30 Thu**, after close, weekend next | 2 working hours → **Sun 10:30** |
| Bug S1 · 24h | +24 hours | 1 working day (same time next working day) |
| Bug S2 · 7d | +7 days | 7 working days |
| Complaint · 24h | +24 hours | 1 working day |

"24 hours" deliberately became **one working day**, not 24 working hours — a human writing a 24-hour
SLA means "by this time tomorrow"; 24 working hours would silently stretch it to 2.7 days.
Degradation: an unusable calendar (no days, inverted window, missing row) falls back to the exact
pre-F28 wall-clock arithmetic — a deadline is never the reason a create fails. The probe sweeps
every hour of a full week × 3 severities: **504 deadlines, 0 outside working hours**.

**The removal.** `fiscal_year_start_month` had no plausible consumer (no financial-reporting surface
exists), so upgrade 012 drops the column + CHECK, and the settings UI control — whose hint claimed
"Used for fiscal-year reporting in dashboards" — is gone. `PATCH /workspace` ignores the key (this
endpoint picks known fields); the GET no longer exposes it; a spec pins the absence.

## 3. D12.3 — the checklist assignee gets its UI; items stay date-free (ISS-070)

`checklist_items.assignee_id` always existed, validated properly (unknown id / invited user → 422)
— and **no screen ever rendered a control for it**. Measured: 14 demo checklist items, zero with an
assignee. `ChecklistsSection` now has a per-item assignee Select (active members only, matching the
server's refusal of `invited`).

The **due-date half of ISS-070 is refused**, per D12.3: an item-level date would be a second deadline
system that My Work, Agenda, the overdue KPI and the calendar would not read; a subtask remains the
primitive for "who, by when". Recorded in the component comment where the next person will look.

## 4. D12.4 — the SLA breach queue exists (ISS-082)

`GET /sla/breached` shipped complete and tested (§29) and had **zero client callers** — there was no
`slaApi` at all. New `/sla` page: breached bugs/complaints, overdue-by (60s refetch), deadline,
assignees with **Unassigned in red** (the most actionable row), linked from the Sidebar and from
Home's `slaBreaches` KPI tile (the tile F24 made truthful, which until now linked nowhere). The nav
entry is deliberately **ungated** — the endpoint is 🔐 any-member and the catalog has no `sla.view`
key; gating the nav on a permission the route doesn't check is the Block F disease in the other
direction. Sequenced after F3/F4 exactly as ISS-082 asked (a UI on a 6-hours-wrong report would
have amplified the error). KB + route-parity map updated — the parity guard caught the new route
before the KB knew it, precisely as designed.

## 5. D12.5 — the locale control stops lying (ISS-028)

"Default locale" was a fully-editable Select whose choice was dropped by `workspaceToWire` before
the request was built — and would have been 422'd if it had arrived — under a success toast. Three
layers disagreeing. It is now **disabled with the Workspace-ID treatment** ("Cannot be changed — the
app ships in one locale"): nothing in the client reads a locale, so a working control would store a
value with no consumer — the ISS-029 defect this same phase removed elsewhere.

## 6. D12.6 — `DELETE /api/v1/sprints/:id` (ISS-013)

A sprint could never be removed — a typo'd name or wrong dates were permanent, cleanup meant SQL.
Built behind `sprint.manage` (the grant that creates one; no new key), with two properties pinned by
14 new specs:

- **Tasks are detached, never deleted** — the schema's existing `ON DELETE SET NULL` does it in the
  same statement; the count is logged and recorded in the workspace-activity row.
- **An ACTIVE sprint is refused** (`409 sprint.active_immutable`) — one click must not silently
  un-sprint work in flight. Close it first. Serialised on the workspace lock like start/close, so a
  delete cannot interleave with a status transition.

## 7. D12.7 — `PATCH /lists/:id { space_id }` moves a list (ISS-036)

A list created in the wrong department was stuck there; the only escape was a replacement list and
a hand-move of every task (no bulk move exists). Now: resolve-and-guard in the service —
`404 space.not_found` (unknown or foreign workspace) · `409 space.archived` ·
`409 list.duplicate` against F27's unique index, case-insensitive, checked against the **incoming**
name when the patch also renames, with `withDuplicateName` still the race-safe arbiter. A move to
the current space is a no-op. **Documented loudly:** reach is space-scoped, so a move changes who
can see the list's tasks — that is the feature, and API_DESIGN says so before someone is surprised.

**The `is_private` half of ISS-036 is refused on purpose** — `lists.is_private` is enforced nowhere
(`rbac/scope.ts`), so a working toggle would be a control that visibly does nothing. A spec now pins
the refusal so a future "consistency" patch has to argue with a test.

## 10. What F28 found and did NOT fix

- **ISS-095 (filed, X1):** `POST/DELETE /tasks/:id/tags*` carry no permission gate — a guest can
  re-tag every task in the workspace. Found *because* the D12.1 fallout mapped exactly onto the
  revoked keys except these two routes, which kept passing with a guest. Grant-matrix can't close
  it (no key exists); it needs the D3.1 compose treatment (`task.edit`) in the P12–P15/P20–P22
  backlog or the F31–F34 sweep. The watcher routes looked identical and are not — they are
  `/watchers/self`, a personal subscribe, correct for a read persona.
- **Guest UI gating:** a signed-in guest still SEES controls their grants will refuse (assign,
  checklist add, the new assignee picker) — P29–P30's client action-gating backlog, unchanged in
  scope by this phase, now with a smaller grant set to gate against.
