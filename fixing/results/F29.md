## 1. ISS-039 — the schema's oldest unkept promise

`schema/tasks.ts` has said since P11 that the engineering columns are *"NULL for non-dev task types
and gated by `task_types.is_dev_type` in the application layer"* — and no layer enforced it, so a
Marketing "Campaign" could carry `branch_name`, a PR link and `bug_severity: S1` (the issue's
verified repro), and the drawer's Git panel rendered all of it.

The gate refuses with **422, never a silent NULL** — dropping a field the caller explicitly sent is
the family of lie Block F existed to remove. Two keys, deliberately different:

| fields | key | error |
|---|---|---|
| `story_points`, `reviewer_id`, `branch_name`, `pr_url`, `pr_status` | `is_dev_type` | `422 task.not_dev_type` (details name the offenders) |
| `bug_severity` | the type is **bug-named** | `422 task.severity_requires_bug_type` |

Severity keys on the NAME because that is the key §29's SLA switch and the S2 default have always
used — so severity and its SLA now travel together, and the issue's sharpest wrinkle (*"looks like
an S1 bug and is invisible to every SLA view"*) is unrepresentable. It also means the eng
report-bug flow and every bug-named workspace type keep working with zero re-flagging.

Three properties beyond the plain refusal:

- **Checked on the RESOLVED type** — explicit body value, list default, or fallback: same gate.
- **PATCH gates on the type the task will HAVE**: `{task_type_id: <dev>, branch_name}` in one
  request is fine; the same patch onto a non-dev target refuses.
- **Re-typing RESHAPES the task**: moving it onto a non-dev type clears the STORED git fields, a
  stranded severity, and — when the new type has no SLA policy — the `sla_due_at`, in the same
  write. Without this, the task kept last month's branch name forever: the exact ghost data the
  issue is about, one PATCH later.

`sprint_id` is deliberately NOT gated (documented in the code): sprint membership has its own
endpoints with its own grant, and attaching non-dev work to a sprint is established, tested
behaviour of that surface. `reporter_team` is not either — complaints are a non-dev type and
legitimately carry it.

## 2. ISS-043 — phone and money finally validate what their names promise

**phone.** The regex `^01[3-9]\d{8}$` existed since P12 and **never once ran**: it was gated on
`config.default_country === "BD"` and nothing ever set that. BD is now the default (this is a
Bangladesh business); the local, `+880` and bare-`880` spellings all pass and are stored verbatim
(validation, not normalisation); a field opts out by configuring another country. ISS-043's own
repro — `01234567890`, the invalid prefix — is a 422 at last.

**money.** Integer and non-empty currency were already enforced; the rest was not, so an "Order
value" could hold **−500 NOTACURRENCY**. Now: negative amounts refused (a refund is its own record,
not a negative order — this field feeds reports and the customer-facing form intake), and the
currency must be a real ISO-4217 code — uppercase three letters checked against ICU's list
(`Intl.supportedValuesOf("currency")`, 162 codes, no dependency; a small-ICU runtime degrades to
the format-only check rather than refusing everything, and the probe is the tripwire for that).

## 3. ISS-045 — `pr_url` joins the URL rule it always compared against

`logo_url` (P6) and `avatar_url` (P7) have refused `javascript:` since their phases; `pr_url` — the
one the drawer renders as a clickable "open PR" link — was checked as a plain string and stored
`javascript:alert(1)` verbatim. Both task validators (create + update) now carry the same http(s)
custom check; `null` still clears. With ISS-039 in the same phase, the field is doubly contained:
it must be a real URL *and* it only exists on dev-type tasks.

## 4. ISS-068 — both doors to the unbounded checklist, capped together

`texts` was `isArray({min: 1})` with no max — 5,000 items in one transaction, and since
`GET /tasks/:id/checklists` embeds items unpaginated, **every later read of that task paid for it
forever**. P27's update found the second door: a template structure carrying 2,000 items was
accepted, and applying it would materialise all of them around any bulk cap.

Both are bounded at **200** — copied from `bulkTasksValidator`, the only other bulk write in the
API, exactly as the issue prescribed. Atomicity was already correct (nothing written on a 422); the
new specs pin cap-exact (200 passes) and cap+1 (201 refuses, zero rows).
