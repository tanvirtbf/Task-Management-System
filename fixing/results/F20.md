# F20 — Search (ISS-074 · ISS-075 · ISS-076, decision D9)

**Status:** DONE
**Fixes:** all three, on D9 (better LIKE — no FULLTEXT)
**Risk taken:** 🟢 — one repo's predicate + ordering, one validator line
**Gate:** `search` in the consolidated run · a 10-request latency sample vs the P40 figure
**Data left behind:** none

---

**ISS-074 — the description is searched.** `like(tasks.description, pattern)` joined the predicate.
For the ops teams the description is where the order number and SKU live — and comments were already
searched, so its absence was an inconsistency, not a policy. Proof: the P25-shaped fixture (needle
in a description only) is found, and `SKU-8841` buried in a description resolves.

**ISS-075 — relevance, not insertion order.** Tasks were `ORDER BY internal_id ASC`: at a few
thousand rows the limit filled with the OLDEST matches and the wanted task was never on the page.
Now a ladder: exact `custom_id` → exact name → name prefix → name substring (a name match outranks a
description-only match) → newest first within each band. Users got prefix-first + alphabetical.
Lists/spaces/comments had already been fixed to name/recency order. Proof: the exact-name match is
FIRST, name@2 ranks above description@3, and `ORD-1042` floats its task to the top.

**ISS-076 — metacharacters + a minimum.** `escapeLike` already existed (it arrived with RBAC P18) —
the missing halves were the validator minimum (one keystroke ran five un-indexable `LIKE '%x%'`
scans; `q` is now 2–200) and the ordering above. Proof: `"100%"` matches the literal task,
`snake_case_name` matches literally, a lone `%` and a single character are 422.

**The D9 boundary, restated:** zero FULLTEXT indexes existed and search was already the slowest
endpoint at 125 ms — index builds + tokenizer tuning inside a fixing phase is risk without a
demonstrated need at ~5k tasks. The relevance sort costs nothing measurable: **p50 32 ms / max 38 ms**
over 10 requests against the demo set (the P40 figure was 125 ms on the 5k-task fixture; different
set sizes, but a 4× headroom to the old number with the new ORDER BY is the regression check the
plan asked for).
