## 1. ISS-016 — a token with no `exp` was a permanent credential

`expressjwt` validates `exp` only when one is present, so a signature-valid token signed with
`noTimestamp: true` was accepted forever — and since access tokens are never checked against the
`sessions` table, nothing (logout, reset, deactivation) could revoke it. That turns a one-time secret
leak into unrevocable access, which matters here: this repo's own secrets were committed once.

`middlewares/authenticate.ts` is now a thin wrapper that requires `exp` after verification and
raises express-jwt's own `UnauthorizedError`, so the response is the same 401 `auth.invalid_token`
envelope as every other malformed token. Verified: exp-less → **401** (was 200), normal token → 200,
expired token → 401 (control).

## 2. ISS-021 — D4: the live check

The access token carries a `role` claim frozen at sign time, and eight service-level gates trusted
it. `rbac/scopeGuard.ts` gained `liveLegacyRole(fallback)`: the RBAC resolver **already** reads the
live user row on every authenticated request (`getActorContext`, version-stamped cache), so the fresh
role was already paid for — this hands it to the gates. Falls back to the JWT claim only where
staleness cannot exist (background jobs, direct-service unit tests, no user actor).

Swapped, 8 sites: `TaskWriteService.del` (hard-delete floor) · `CommentsService.delete` ·
`AttachmentsService` ×3 (two guest upload checks + `softDelete`) · `UserService.updateProfile` ·
`ReportsService` ×3 `isAdmin` callers · `ReviewsService` ×2.

```
live admin, hard delete                       204
owner demotes them to member                  200
SAME old token, very next request:  hard delete  403     (was 204 for up to 15 minutes)
                                    soft delete  204     member powers intact
```

**What D4 does not change:** the ≤15-minute window on plain *logout* and *deactivation*
(ISS-018) — those are about the token still authenticating at all, not about which role it claims.
The bound is unchanged, re-measured below, and stays the documented auth-layer decision.

## 3. ISS-015 — change-password now evicts other sessions

The two password paths disagreed and the more common one was the unsafe one: reset revoked every
session, change did not. `AuthService.changePassword` now calls `revokeAllForUser` after the hash
write — the same line the reset path always had.

```
3 devices signed in                     live sessions 3
POST /auth/change-password  -> 204      live sessions 0      (was: unchanged)
another device's refresh    -> 401                           (was: 200, still signed in)
sign in with the NEW password           200
```

## 4. ISS-017 — the session table stops growing without bound

Refresh rotation INSERTs, and cleanup keyed only on `expires_at + 30d`, so a revoked row survived
~60 days → a projected ~190k-row steady state at 100 users. `sessionCleanup` gained a second rule:
**`revoked_at < now − 7 days`**. A revoked session can never authenticate again; seven days keeps a
forensic window and drops the projection to ~23k rows. `TokenService` gained
`countRevokedBefore`/`deleteRevokedBefore` plus `countPrunable` (an OR-count, so the dry run cannot
double-count a row both rules match).

```
seeded: expired-31d · revoked-20d · revoked-2d · active
dry  -> {processed: 2, wouldDelete: 2}
live -> {deleted: 2, deleted_expired: 1, deleted_revoked: 1}
kept -> ["s-F10-active", "s-F10-revoked2"]      the 30-day rule is untouched
```

The existing spec was updated rather than worked around: the old test asserted "a revoked session is
kept until expiry + 30d", which is exactly the behaviour ISS-017 filed. It now asserts the new rule,
plus a new case for the fresh-revoked row that must be kept.

## 5. ISS-018 — re-measured, still documented

```
logout                     -> 204
refresh with the cookie    -> 401     the window cannot be renewed
old access token, /auth/me -> 200     accepted for the remainder of its ≤15 min
```

Unchanged by design. D4's live check means a *demoted* user loses the elevated gates immediately;
this row is about a *logged-out* user's token still authenticating, which only a session-table check
on every request (or a shorter TTL) would close. The user chose the live check and not the TTL cut,
so the bound stays — now with the F10 measurement attached to it.

## 6. Two fixtures the gate caught (and one correction)

**33 users tests went red on the first gate run — all fixture, none product.** `seedUsers` in
`users/list.test.ts` + `get-by-id.test.ts` bulk-inserts `users` rows DIRECTLY (the point: controlled
ids in one round-trip), skipping the `syncUserSystemRole` call every real creation path runs. A user
with no `user_roles` row holds nothing — “authenticated but powerless” is a valid state the resolver
documents — so once **F7** put a `member.view` gate on `GET /users`, the seeded CALLER 403'd on its
own workspace. **F7's gate list never included `users`**, which is why this surfaced two phases late.
Both helpers now assign the system role (`bump: false` — brand-new accounts, no cached actor, and N
bumps would serialise on the workspace row).

**52 `signAccess` helpers gained a default `expiresIn: "15m"`.** ISS-016 made `exp` mandatory, and an
opts-less `signAccess(u, SECRET)` mints a token with `iat` but no `exp` — so a helper whose callers
mean “a normal valid token” started producing an invalid one. Only 2 call sites were actually
affected today; the default fixes the latent trap in all 52 files at once. Calls that pass
`expiresIn: -10` still override it (the expired-token cases stay red-for-the-right-reason).

**ISS-093 was mine to correct.** F3 filed “a users test has been failing since 2026-07-30” and named
the wrong test — I read the name off a run I had KILLED, where jest lists every test in the file.
Run to completion here, the survivor is the **50-parallel-read concurrency test** — ISS-087, already
filed, owned by F11, and the exact twin of the `tasks` module's one failure. ISS-093 is closed as a
duplicate; its PROCESS half (a sweep nobody read back; a killed run treated as evidence) is kept as
F32's requirement.
