## 1. SCAN-M5 — the Engineering block rendered unconditionally

It sat **outside** the conditional that gates Department and Reports, so every Marketing-only user
saw Eng Home, Sprint Board and On-call rotation. There is no `eng.view` permission in the catalog,
so the gate is "holds any engineering-domain grant", measured against the seeded roles:

```
owner                  holds all four            -> sees it
jhankar (an engineer)  sprint.assign_tasks +
                       postmortem.manage         -> sees it
marketing.only@        none                      -> hidden
guest@                 TWO of them (ISS-094)     -> hidden, by the role term
```

**Report a bug stays outside the gate** — reporting a bug is precisely how a *non*-engineer reaches
the engineering team.

### The finding this turned up: ISS-094

The seeded **Guest** role holds `postmortem.manage` and `sprint.assign_tasks` at `scope = all`.
Since F7 those are real route gates, so a guest can file a postmortem and move tasks in and out of
sprints. Filed as **ISS-094** and left unfixed here (rule X1 — and it is a grant-matrix decision,
which belongs with F28).

It does constrain this gate, though, and the constraint is worth stating: a grant-only test would
show a guest the whole Engineering section, while narrowing to `sprint.manage|oncall.manage` would
hide it from real **engineers**, who hold neither. So the gate is *(any engineering grant) AND role
≠ guest* — correct today, still correct after ISS-094 is fixed, and the code says to drop the extra
term then.

## 2. SCAN-M5 (wider) — the action buttons, scoped

Per the answered scope question: **nav + high-traffic actions**, not all 56 permissions (RBAC plan
items P29–P30 already own that surface).

| control | gate |
|---|---|
| Workspace settings / Members / New space (sidebar menu) | `workspace.settings` / `member.view` / `space.create` |
| Invite member | `member.invite` |
| Archive / Restore a task | `task.delete` |
| Delete permanently | `task.delete_hard` |
| Status reorder arrows (§3 below) | `status.manage` |

The routes were already wrapped in `<RequirePermission>`; what rendered regardless were the entries
*leading* to them, so a member clicked through to a Forbidden page. The probe also checks the other
direction — that the **server** refuses what the client now hides (`marketing.only@` inviting → 403).

## 3. ISS-042 + ISS-023 — the guest-redaction control, connected at both ends

`custom_fields.hidden_from_guests` drives real redaction (`TasksRepo.customFieldValuesByTask(ids,
redactGuest)`) and appeared in **no validator and no serializer** — the one guest-redaction control
the product implements could only be switched on by editing the database by hand. It is now on the
wire: create accepts it, PATCH toggles it, a non-boolean is a clean 422, and every wire custom field
carries it.

ISS-023 is the other end of the same feature: **one of eleven** call sites passed a literal `false`
(`ReviewsService`), so a guest reading the review queue would have seen values the other ten redact.
It computes `redactGuest` like its siblings now. The two were latent together and are fixed
together — connecting ISS-042 without ISS-023 would have shipped a control with a hole in it.

## 4. ISS-038 — the reorder endpoint gets its first caller

The server endpoint worked and the client even had a typed wrapper, `statusesApi.reorder`, with
**zero callers** — so board column order was frozen at whatever the list defaults created, and a new
status was appended forever.

`/settings/statuses` now has **move-earlier / move-later** arrows per status. Not drag-and-drop: the
page is a read-only summary today, this needs no new dependency, and — the deciding reason — F18
made the endpoint require a **complete permutation with distinct positions**, which a swap satisfies
by construction while a drag library's incremental payloads would not. The probe builds the exact
payload the arrows build and proves the server accepts it, then restores the original order.

Evidence: `f26-probe.cjs` / `.txt` — 22 checks, exit 0, including live `/me/permissions` reads for
all four demo personas.
