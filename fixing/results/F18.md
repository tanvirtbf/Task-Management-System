# F18 — Validation holes and contract self-contradictions (six issues)

**Status:** DONE
**Fixes:** ISS-044 · ISS-071 · ISS-077 · ISS-032 · ISS-037 · ISS-078
**Risk taken:** 🟢 — every change makes the API refuse *more*; no schema, no data
**Gate:** the consolidated final gate (`F16/gate-final.txt` — tasks/attachments/forms/spaces/statuses
all in it)
**Data left behind:** none — baseline verified to the statuses count (65)

---

Six holes, one probe (`f18-probe.txt`, 16/16). Each check asserts the right 4xx **and** that the
matching happy path still works — a validator that refuses everything also "fixes" a 500.

## 1. ISS-044 — `reviewer_id`, the one unvalidated reference on create

Every other reference on `POST /tasks` fails clean (`status_id` 422, `assignees` 422, list 404…);
an unknown `reviewer_id` was a raw FK 500. `create()` now runs the **same check `update()` has
always had** (`task.invalid_reviewer`, active-member rule). A valid reviewer still lands on the
created task.

## 2. ISS-071 — the 300-character filename

The presign path has always refused a long `filename` with a 422; the **proxied path — the one the
shipped client actually uses** — passed `X-Filename` straight to an insert into `varchar(255)`, and
MySQL's "Data too long" surfaced as a raw 500. The controller now applies the same 255 rule, counted
after URI-decoding (which is what is stored). 296+4 chars → 422 naming the header; 244 chars → 201
as before.

## 3. ISS-077 — the API rejected its own slug

`slugify()` lowercases the title, then a **mixed-case** random token was appended — and `SLUG_RE`
allows lowercase only. So every generated `public_slug` was un-writable-back: PATCH a form with its
own unchanged slug → 422. The fix is the issue's own suggestion: lowercase the token. Generated
slugs now match `SLUG_RE`, and the echo-back PATCH returns 200.

## 4. ISS-032 — `POST /spaces` silently dropped the head

POST performed none of the checks PATCH does and dropped whatever it could not use — 201,
`head_user_id` NULL, no error. Now one rule, both paths:

- the update validator's `head_user_id` shape rule, added to the **create validator**;
- the service's three checks (exists in this workspace / active / not a guest — all 422
  `space.head_invalid`) extracted to one `assertValidHead` used by create *and* update, so the two
  can never drift apart again;
- the value is carried through controller → service → repo and **written**;
- and the same **permission** PATCH acquired in F7: installing a head at create time now requires
  `space.head_assign` too — without it, create was a bypass around the gate F7 built.

Explicit `null` still creates headless (nothing is being assigned). Proof: unknown head 422, guest
head 422, valid head **written to the row**, null 201.

## 5 + 6. ISS-037 / ISS-078 — the two reorders now demand a permutation

Both endpoints validated items well (ids, ownership, duplicates) and then accepted sets that destroy
the order anyway: every status at position 0 → 200; one item of three → 200 with two rows colliding
at 0. For the form case that means the **public form could render its questions in a different order
on different requests** (`ORDER BY position` over ties is arbitrary) — and the reorder said 200, so
nothing could notice.

Both now enforce the issues' own Expected line — **the full set, exactly once, with distinct
positions** — as 422s with messages that say what was missing (`got 1 of 5`). A full valid
permutation works as before, proven by actually flipping the order both times.

*Why "require the full set" and not "renumber the remainder":* the alternative silently rewrites
positions the caller never mentioned; a refusal that names the rule is the honest contract, and it
is also what both issues ask for first. The client sends full sets (ISS-038 notes the status one is
not wired to the UI at all yet), so nothing breaks.

## 7. Nine tests asserted the OLD behaviour, and were updated with the reason

The consolidated gate surfaced them: **8 reorder specs** (three literally pinned ISS-037 —
*"accepts a partial subset"* asserted the two-statuses-at-0 collision as CORRECT; *"allows
duplicate target positions"*; *"accepts a single-item array"* — and five more whose fixtures sent
partial payloads incidentally) and **1 unarchive spec** (*"does NOT restore the space's archived
lists"* — ISS-041's bug as intended behaviour; its fixture even reused the SAME `ARCHIVED_AT`
constant for the space and the 'independent' list, unknowingly forging the cascade's signature).
Each was rewritten to the new contract with the ISS number in a comment; the unarchive spec now
proves BOTH sides — the cascaded list returns, a genuinely independent one (a different instant)
stays archived.

After the updates: **statuses 209/209 · spaces 244/244** — the full 8-module gate is green.
