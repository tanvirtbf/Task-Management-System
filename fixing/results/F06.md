# F6 — Map every route to its permission (Block B's design pass)

**Status:** DONE

**Risk taken:** 🟢 analysis only
**Deliverable:** `fixing/evidence/F06/ROUTE_PERMISSION_MAP.md` + the re-runnable census

## 1. What was produced

**The census** — a script, not a transcription: it imports the real catalog (56 keys) and slices
every router file into per-registration blocks, resolving gates bound to consts
(`const gate = requirePermission("x")`). Result: **181 routes — 61 permission-gated (27 distinct
keys), 104 authenticate-only, 16 public.** The 29 catalog keys with no route gate decompose exactly
into: the 21 NOT-ENFORCED (F7's job), 3 service-enforced (`review.read`, `report.generate`,
`report.note`), 2 visibility-machinery keys (`space.view`, `task.view`), 2 testing-unresolved
(`review.perform`, `form.view_submissions`), and 1 genuine catalog-invariant violation
(`space.head_assign` — see §3).

**The route→permission table** — all 21 keys assigned: **17 are mechanical route-middleware
additions (34 sites)**, 4 are service-shaped composes, plus `report.view` (service-shaped) and the
`space.head_assign` bonus row. Every GET that deliberately *stays* authenticate-only is listed with
its reason, so F7 (and any later audit) can tell "ungated by design" from "forgotten".

**The role→grant matrix** — the harder half, and the best news of the phase: **no grant changes are
needed.** `SYSTEM_ROLE_GRANTS` in `rbac/bootstrap.ts` already encodes today's effective behaviour
for all 56 keys and is pinned by a snapshot test. Both rows that looked like seeded-vs-actual
divergences were run down and are not: guests genuinely cannot upload today (legacy `Roles.GUEST`
checks in `AttachmentsService`), and "any member can GET /reports" is an **empty head-scoped
list**, not read access. F7's Side 1 collapses to an assert against the live `role_permissions`.

## 2. The two decisions the plan delegated to this phase

**Compose, not replace** (the plan's own recommendation, adopted with one refinement). Feature-logic
branches — self, author, uploader, department-head — are not role hierarchy and stay untouched; the
**admin/owner branch** of each legacy check becomes `legacyAdmin && holds(key)`. Seeded roles behave
exactly as today; un-ticking a toggle now takes real effect (D3's point); granting one of these keys
to a non-admin custom role does nothing — **compose cannot widen access**, which is why it beats
replace. The refinement matters most for `report.view`: a route gate there would 403 every
department head (legacy `member`s) and break dept-review — the head branch must stay feature logic.

**The three odd routers** (`search.ts`, `home.ts`, `me.ts`): **no gate, by design.** They are
self-scoped surfaces (own dashboard, own permission set, visibility-scoped search); no catalog key
fits, and catalog invariant #1 forbids inventing keys that gate nothing real. Recorded in the map's
§4 with the rest of the deliberate leave-alones (notifications, SSE, watcher self-toggle, comment
self-edit).

## 3. Found while mapping (recorded, not fixed — rule X1)

- **`space.head_assign` is enforced nowhere** — the key exists in the catalog and the seeded
  grants, and no code checks it; head assignment rides `PATCH /spaces/:id` under `space.edit`. That
  violates the catalog's own invariant #1 ("a key that gates nothing is a lie"). The map adds it to
  F7 as a body-conditional service check rather than filing a new issue — it is squarely inside
  ISS-024's "toggles that do nothing" and D3's mandate.
- **F7 needs one new primitive:** `assertCan(key)` — the service-layer half that
  `middlewares/requirePermission.ts:16-20` has promised in a comment since P11 and that was never
  built (the SCAN-H1 note). Same ALS resolver, throwing the same 403 shape.
- **Blast radius worth naming:** the public form submit creates tasks through `TaskWriteService`
  with no HTTP actor. Route gates never touch it; `assertCan` sites were chosen so none sit on a
  public/job path.
