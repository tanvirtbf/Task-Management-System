# F25 — Task UI gaps (ISS-050 · ISS-054 · ISS-055 · ISS-066 · ISS-069)

**Status:** DONE
**Fixes:** all five
**Risk taken:** 🟢 — mostly client; one server-side reference resolver
**Gate:** client `vitest` · jest `collab` + `taskdeps`
**Data left behind:** none

---

## 1. ISS-050 — "Delete" was not a delete, and neither action could be undone

`DELETE /tasks/:id` is a **soft** delete: it sets `archived_at` and the task stays fully readable.
So the drawer's "Archive" and "Delete" were two labels for one operation — a user who clicked
Delete believed the task was gone while anyone with the id could still read it. And there was no way
back: `POST /tasks/:id/unarchive` works perfectly server-side and had **zero callers** in the client.

Now:
- `tasksApi.unarchive` exists, and the drawer's menu **toggles** — "Archive" on a live task,
  **"Restore"** on an archived one.
- "Delete" became **"Delete permanently"**, sends `?hard=true`, and asks first — the confirm names
  what goes with it (comments, checklists, attachments) and points at Archive as the reversible
  option.
- The bulk toolbar got the same treatment, including the Archive confirm saying the tasks stay
  restorable.

## 2. ISS-054 — the "Blocked by" direction was unreachable

The component held `showPicker: "blocks" | "blocked_by"`, rendered a **Blocked by** group and styled
it in the danger colour — but the single Link button hardcoded `"blocks"` and the mutation never
read the direction. Two buttons now (**Blocks** / **Blocked by**), and the mutation maps the
direction onto the stored edge: the edge is always `(task_id BLOCKS related_task_id)`, so
"blocked by" simply sends the pair reversed.

## 3. ISS-055 — the picker could only see one list

The API has always allowed a dependency between any two tasks in the workspace, and the most
valuable ones here cross departments ("Marketing's launch banner blocks Engineering's release") —
which could not be created in the UI at all. The picker now **searches**, which is workspace-wide,
visibility-filtered server-side (RBAC P18), and relevance-ranked since F20.

> **The probe caught a bug in this very change.** The first cut sent
> `types: ["tasks"]`; the valid `SearchType` is **singular** (`"task"`), and the service silently
> drops unknown tokens — so the picker would have searched *nothing*. Exactly the "accept and
> discard" failure mode F23 spent a phase removing, reintroduced by me and caught because the probe
> asserted a real search result rather than the code shape.

## 4. ISS-066 — `#T-<n>` now resolves, and only where it can

The client renders a task's key as `custom_id ?? "T-" + task_number`, and **43 of 46** live tasks
have no `custom_id` — so the identifier people read, and therefore type, was the one the resolver
did not understand.

**The scoping is the whole design decision.** `task_number` is unique **per list**, not per
workspace: thirteen tasks in this workspace are "T-1". A workspace-wide lookup would have to guess
between them. So `#T-<n>` resolves **inside the host task's list**, where the number is unique by
construction and where the reference almost always means a sibling on the same board; a `T-<n>` from
another list stays unresolved, which is the honest outcome. `#CUSTOM-ID` is tried first and is
unchanged.

## 5. ISS-069 — checklists nest on the server, flat on the client

Items arrive as a flat array carrying `parent_item_id`; the client rendered them all as siblings and
offered no way to create a sub-item. It now builds the tree (order preserved — the server sorts by
`position`), indents each level with a cap so a deep tree stays readable, and every item has an
**add sub-item** control. The api wrapper forwards `parent_item_id`, which the server has always
accepted.

Evidence: `f25-probe.cjs` / `.txt` — 22 checks, exit 0. Each client fix is checked twice: the server
behaviour it now relies on, exercised live, and the client source asserted to have stopped doing the
wrong thing.
