# F8 — Scope narrowing: `own` / `own_space` / `space` (ISS-047)

**Status:** DONE
**Fixes:** ISS-047 (HIGH — an `own`-scoped `task.edit` edited someone else's task)
**Risk taken:** 🟡 — a new check on every task write, held to zero cost and zero behaviour change
for full-reach grants
**Gate:** the scope probe **21/21, exit 0** · jest `rbac` + `tasks`, serial
**Data left behind:** none — users 15, tasks 46, roles 5, notifications 57; the ISS-025 column

## 1. The missing half, built where the resolver already lived

The RBAC resolver could *always* answer the scope question — `decide(actor, key, {spaceId,
createdBy, assigneeIds})` handles `all` / `spaceIds` / `own` / `ownSpaceIds`, and
`/me/permissions` faithfully reported all four. **Nothing on a write path ever asked it.** The
route middleware asks the verb question by design ("holds it anywhere?"); the object question needs
the resolved row, which only the service has.

F8 adds that call — nothing else. No new resolution logic, no schema, no grant changes:

| piece | what |
|---|---|
| `rbac/scopeGuard.ts` *(new)* | `assertScoped(key, ctx)` — resolves the ALS actor, delegates to `assertCan`; **no-actor contexts pass** (jobs, seed, the anonymous public-form submit — each has its own boundary, and scope is a statement about a user's grant). `hasFullReach(key)` — true for `all`-scoped grants, so callers skip context-building entirely. |
| `TasksRepo.spaceIdsByTask` *(new)* | task → its primary list's space, batched — tasks carry no space column, and the guard needs one |
| `TasksRepo.TaskHeader` | gained `createdBy` (the membership service authorises from the header) |
| `TaskWriteService` | guards on **create** (target list's space, `isOwn: true`), **update** (the ISS-047 surface), **archive**, **unarchive**, **delete** (soft *and* hard — the hard path keeps its F7 compose on top), **bulk** (fail-atomic across every target, one batched context build) |
| `TaskMembershipService` | guards on **addAssignees** / **removeAssignee** (`task.assign`); the watcher self-toggle deliberately untouched — self-scoped by design |

**The hot path pays nothing.** Every seeded-role grant is scope `all` (asserted in the probe:
0 non-`all` rows for the four system roles), and `hasFullReach` short-circuits before any lookup —
so the ~3,500 existing tests and every current user run exactly the code they ran yesterday, minus
one in-memory map read.

## 2. Proof — `f8-scope-probe.txt`, 21/21

**The issue's own account** (`marketing.only@`, `task.edit` @ own, space-assigned →
`ownSpaceIds=[Marketing]`):

```
their own Marketing task                         PATCH -> 200
a task they are ASSIGNED to (not creator)        PATCH -> 200   own = creator | assignee
someone ELSE's task, inside their visible space  PATCH -> 403 task.forbidden / not_own
                                                 …and the DB value did not change
```

That third line is ISS-047's repro verbatim, with the P42 gotcha respected — the target sits in a
*visible* space, so visibility says yes and the refusal is provably the scope check.

**The other scopes, via a probe role** (`task.create`/`task.assign` @ space:Marketing,
`task.archive`/`task.delete` @ own, plus a workspace-wide viewer role — without the viewer, the
space assignment clamps `space.view` too and the outside-space probes die as **404s at the
visibility layer** before scope is ever consulted; the probe records that deliberately):

```
create INSIDE the assigned space     201        create OUTSIDE it   403 out_of_scope
assign inside                        204        assign outside      403
archive their OWN task               204        someone else's      403 not_own
delete someone else's                403
bulk [own, foreign]                  403 whole  bulk [own]          200
```

**And the two invariants:** a plain member still edits anyone's task (seeded behaviour unchanged),
and the anonymous public-form submit still creates its task (the no-actor carve-out — proven live
with the ISS-025 columns temporarily in place, then dropped again).

## 3. Drawn boundaries (recorded, not hidden)

- **Content permissions are narrowed at the route only.** `comment.create`, `checklist.manage`,
  `attachment.upload`, `dependency.manage`, `customfield.set_value`, `sprint.assign_tasks`,
  `template.apply`, `postmortem.manage` offer `space`(/`own`) scopes in the catalog, hold F7's
  verb-level gates, but do not yet consult scope against the resolved row. The plan scoped F8 to
  the task family (its verify + its `rbac`,`tasks` gate say so); the same 5-line pattern extends to
  those services when a phase owns them. This is the P20–P22 remainder in the RBAC plan's open
  list, now with a ready-made mechanism.
- **Reads were already scoped** by the visibility layer (P5's 84-read IDOR sweep, re-confirmed
  here by the 404s) — F8 changes no read.
- **Tags attach/detach** (`POST/DELETE /tasks/:id/tags`) remains authenticate-only — it was outside
  ISS-024's 21 and has no catalog key; noted in F6's map §4 terms.
