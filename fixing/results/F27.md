# F27 — Names and duplicates (ISS-033 · ISS-035 · ISS-027 · ISS-026, decision D11)

**Status:** DONE
**Fixes:** all four
**Risk taken:** 🟡 — three new unique indexes; a write that used to succeed can now 409
**Schema (X4):** `database/upgrades/010_name_uniqueness.sql` + `database/schema.sql` + Drizzle
(`hierarchy.ts`, `rbac.ts`)
**Gate:** `spaces` · `lists` · `rbac` · `customfields` · `tags` · `statuses` · `taskTypes`
**Data left behind:** none in the demo DB. **Six rows renamed in `taskmanagement_qa`** — see §4.

---

## 1. The pattern, copied rather than reinvented

Of eight named resources, three enforced case-insensitive uniqueness and five did not — and the
three that worked are the **catalog** resources (statuses, task types, tags) while the ones that did
not are the **navigation** resources, where a duplicate name hurts most. ISS-033's incident was real:
the workspace held two spaces called "Marketing", one with three lists and a head, one empty,
rendering identically in the sidebar tree, and had to be untangled by hand.

The working implementation is a **unique index on a `utf8mb4_unicode_ci` column** plus an
ER_DUP_ENTRY → 409 mapping — which is race-free, needs no application-side `lower()`, and is what
`TagService` has always done. That is exactly what shipped here:

```
spaces  UNIQUE (workspace_id, name)   -> 409 space.duplicate
lists   UNIQUE (space_id, name)       -> 409 list.duplicate     (scope is the SPACE:
                                                                 the same name in another
                                                                 space is still fine)
roles   UNIQUE (workspace_id, name)   -> 409 role.name_taken
```

**D11: enforced on CREATE *and* RENAME.** The three working resources do both, an index cannot tell
them apart anyway, and ISS-033's own repro is two lines — a create and a rename. Asked with data
first: the demo DB had **0 collision groups**, so nothing needed resolving.

**Archived rows are included deliberately.** An archived space can be restored, and a restore that
produced a duplicate would recreate the exact incident. (MySQL has no partial index either, so this
is also the only option.)

## 2. ISS-027 — the role NAME, not just the key

`role_key` was already deduped — by silently **suffixing** it, which is why `role.key_taken` existed
in the catalog and never fired. The display name collided freely, so two roles could look identical
in the roles grid. The name is unique now; the key's suffixing behaviour is untouched.

## 3. ISS-026 — a system role cannot be renamed

`DELETE` refused with `role.system_immutable` while `PATCH {name}` returned 200 — so "Admin" could
be renamed to anything while every UI, every doc and the seeded grant matrix still called it Admin.
The rename guard is deliberately the **same shape** as the delete guard. Description and colour stay
editable: they are cosmetic, the name is the identifier people navigate by. A no-op rename to a
role's own name is not an error.

> **A correction to the issue text.** ISS-026 records the delete guard as *"409
> role.system_immutable"*. Verified live: `DELETE` on a system role has always answered **403**
> (`AppError.forbidden`). The rename guard therefore answers 403 too — consistency with the existing
> guard is the point, and the issue's status line is what was off by one code. The probe asserts
> both endpoints and that they agree.

## 4. The QA database had real duplicates — and that is the useful part

`010` applied cleanly to `taskmanagement` and **failed loudly on `taskmanagement_qa`**:

```
Duplicate entry 'ws-…-P35 Activity Space' for key 'spaces.uq_spaces_workspace_name'
Duplicate entry 'sp-…-Bug Triage'         for key 'lists.uq_lists_space_name'
```

That is the migration behaving exactly as the script documents — naming the colliding value instead
of silently skipping. The QA DB is a scratch database and those rows are test residue, so the six
losers were **renamed** (suffixed `(2)`, `(3)`) rather than deleted — nothing references a name —
and the script then applied 15/15. Re-applying is a no-op (verified: 15/15 twice on both DBs).

Worth carrying forward: **on a database that holds duplicates, this upgrade stops and tells you
which ones.** Resolve them and re-run.

## 5. Twelve specs the new rules touched

| suite | what happened | now |
|---|---|---|
| `spaces/create` ×2, `spaces/update` | *"allows two spaces with an identical body (no unique constraint -> no 409)"* and *"allows renaming a space to match another space's name"* asserted the ABSENCE of the rule as a feature — ISS-033 is the incident that absence allowed | inverted, plus a new spec proving the same name is still legal in a DIFFERENT workspace |
| `spaces/create` ×3 (fixture) | validation loops created several spaces from one `validBody()` — same name each time | distinct names; the colour/position/idempotency subjects are untouched |
| `lists/create`, `lists/update` | the same two shapes, one level deeper | inverted, plus a cross-SPACE negative case |
| `rbac/roles-api` | *"derives a unique key when two roles share a name"* — the suffixing behaviour that made `role.key_taken` unreachable | inverted; a NEW spec keeps the key logic covered via two genuinely different names that slugify alike (`Deal Desk` / `Deal  Desk`) |
| `custom-fields/list` | the wire-shape list predated `hidden_from_guests` (F26) | key added |
| `statuses` ×4 (fixture) | a local `insertList` helper hardcoded `name: "Test List"`, and four specs put a SECOND list in the same space to prove status scoping | the helper numbers its lists; what those specs test is unchanged |

Only the first four rows are behaviour; the rest are fixtures that happened to lean on the missing
rule.

**One of them is a small proof the rule works.** The colour-validation loop was first given names
like `Colour #abcDEF` / `Colour #ABCDEF` — which collided, because those two colours differ only in
case and the name rule is case-insensitive. Indexed names instead.

client vitest 44/44 (`gate-final.txt`).
