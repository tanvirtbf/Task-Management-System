**Status:** DONE

## 1. What was actually wrong

Drizzle's MySQL `timestamp` mapper hardcodes `+0000` in **both** directions:

```js
mapFromDriverValue: (value) => new Date(value + "+0000")
mapToDriverValue:   (value) => value.toISOString().slice(0, -1).replace("T", " ")
```

So it reads every value as if MySQL had rendered it in UTC, and writes every value as UTC. That is
correct **only when the MySQL session is UTC**. The session was Dhaka (`DB_TIMEZONE` empty in dev,
`+06:00` in the production `.env`), so the driver and the database disagreed by exactly six hours on
every TIMESTAMP column — 12 observations in the F1 baseline, in all four configurations.

The bug was never in the application's own date arithmetic. It was one line of configuration.

## 2. The fix — one file, plus the two consequences of it

**`server/.env`: `DB_TIMEZONE=+00:00`.** That is the whole clock fix. Pinning the session to UTC makes
Drizzle's hardcoded assumption true, and all 12 drifting observations go to zero at once.

Users still see Dhaka time: the API emits ISO-8601 (`…Z`) and the client renders it in the viewer's
local zone. The storage clock and the display clock are different concerns, and only the storage clock
had to be pinned.

Two things depended on the *old* session zone and had to move with it:

**(a) DATE columns — write and read had to be re-centred on UTC midnight.** `toLocalDate` built Dhaka
local midnight, which under a UTC session is 18:00 the *previous* day, and a `DATE` column truncates
that to the wrong calendar day. A due date of `2026-08-10` was landing as `2026-08-09`. Drizzle's
`MySqlDate.mapFromDriverValue` does `new Date("YYYY-MM-DD")` — UTC midnight — so the write had to
match it. Renamed `toLocalDate` → `toDateOnly` (the old name asserted the bug) and switched to
`Date.UTC`, in `TaskWriteService` (8 call sites), `SprintsService` (4) and `OnCallService` (1). The
two serializers that render a DATE back out (`taskSerializer`, `onCallSerializer`) switched from
`getFullYear/getMonth/getDate` to the `getUTC*` equivalents. Write and read are now symmetric and
independent of the process TZ.

**(b) The on-call roster — `CURDATE()` no longer means "today in Dhaka".** `on_call_shifts.week_start`
/`week_end` are DATE columns holding *Dhaka business days*, and both live query paths compared them
against SQL `CURDATE()`. `CURDATE()` renders in the session zone, so pinning the session to UTC would
have rolled the roster over **six hours late** — every Monday 00:00–06:00 Dhaka would still have
reported last week's engineer, and the same six hours at the far end would have kept a finished shift
current.

The codebase already had the right tool for this: `utils/dhakaTime.ts`'s `dhakaToday()`, written for
the dept-review work, which derives the Dhaka calendar day from a UTC instant by fixed offset —
independent of both the session zone and the box's TZ. `OnCallRepo.findCurrent` and
`EngineeringRepo.findCurrentOnCallEngineerId` now bind that value instead of calling `CURDATE()`.
Both paths had to move together or a bug's auto-assignee and the on-call board would disagree.

The `v_current_on_call` / `v_breached_sla` views were *already* three-way inconsistent between the
live DB, `schema.sql` and `_post.sql` (logged during the earlier full-system test). Rather than leave
them drifting, `database/upgrades/005_clock_views.sql` re-derives both against the new clock and makes
all three agree. Neither view is read by the application, so this has no runtime effect today — it
stops them lying to anyone who queries them by hand, and to the QA phases that diff view-vs-endpoint.

**(c) Three more places wrote or read a DATE on the wrong footing.** Once (a) established that a DATE
must be built at UTC midnight, every *other* producer of a DATE was wrong by the same argument. I
swept for the pattern (`new Date(y, m-1, d)`, `getFullYear/getMonth/getDate`) rather than fixing only
what I had already broken, and found:

1. **`OnCallService` stored a six-day week.** `weekStartDate` had moved to UTC midnight, but
   `weekEndDate` was still rebuilt from that date's *local* components — mixing frames inside one
   function. `PUT /on-call/2026-09-07` stored `week_end = 2026-09-12` instead of `2026-09-13`, so
   **Sunday had nobody on call.** This is the one that would have hurt: it is silent, it is
   off-by-one, and the endpoint returns 200. Fixed by adding the six days in UTC.
2. **`sprintSerializer.formatWireDate` and `EngineeringService.ymd`** read stored sprint DATEs with
   local components — the read counterparts of a writer I had just moved. Both now use `getUTC*`.
   These are the second and third hand-rolled copies of the same six-line function; the duplication
   is exactly why they could drift apart, and it is noted in the code for a later cleanup (rule X5
   keeps the collapse out of this phase).
3. **`seed-demo.ts` wrote every DATE one day early.** Its helpers built local-midnight Dates, so
   under the new driver every seeded `due_date`, sprint boundary and on-call week landed a day
   before the day it named. Since the seed *is* the fixture every later phase restores to, a silently
   shifted baseline would have quietly poisoned them. Its helpers now derive the day with
   `dhakaToday()` and place it at UTC midnight.

`HomeService.ymd` was deliberately **left alone**. It is only ever called on a now-instant, which
makes it the *business-day* question rather than a stored-DATE question — that is ISS-058, and it
belongs to F5. Changing it here would have been the same mistake as (b) in reverse.

### Checked and safe — do not re-audit

A final sweep for local date components across `server/` leaves exactly these, all deliberate:

| site | why it is fine |
|---|---|
| `validators/onCall.ts:55-59`, `FormsService.ts:111-113` | calendar-*validity* round-trips (build a local Date, read local components back). Self-consistent by construction and never touch the DB, so no zone can be misapplied. |
| `HomeService.ymd` + `tests/home/home.test.ts`'s `ymd` | the business-"today" pair, left matched to each other on purpose. **F5 / ISS-058** — `home` passes 23/23. |
| `tests/eng/report-bug.test.ts:271` | an on-call shift 21 days in the past; hours cannot move it across the window. `eng` passes 78/78. |

**Why `TaskWriteService.ymd` was split rather than switched.** It was called for both jobs — reading
a stored DATE *and* deriving "today". Flipping it wholesale to UTC would have fixed the first and
broken the second, re-introducing exactly the six-hour bug from (b) in the my-work buckets. It is now
`storedDateYmd` (UTC components) and `dhakaToday()` (business day), which is the distinction the
single helper was hiding.

## 4. Two corrections to earlier records

**My own verification script was wrong before the product was.** `f3-verify.cjs` reported ISS-001 as
"STILL BROKEN" after the fix. It was reading the database over its own mysql2 connection, which does
not set a session zone, so it compared a Dhaka-rendered `stored` against a UTC `wire` and found the
6h it went looking for. `frame-note.txt` reads one row under three session frames and settles it:

```
session default(SYSTEM=Dhaka)   stored=2026-08-03 14:37:26   vs wire …T08:37:26Z   drift 6.00h
session +06:00                  stored=2026-08-03 14:37:26   vs wire …T08:37:26Z   drift 6.00h
session +00:00                  stored=2026-08-03 08:37:26   vs wire …T08:37:26Z   drift 0.00h  <- the app
```

Worth stating plainly for whoever debugs this next: **a SQL client must `SET time_zone='+00:00'` to
see what the application sees.** A raw `SELECT` in a default session will look six hours off and is
not evidence of a bug.

**The probe had two stale fixtures.** It looked up a demo space by the name `Politics` and printed
row-count expectations from the pre-reseed baseline — both left over from demo data that the F3
re-seed replaced, and the first one crashed the gate outright. Since F4 and F5 reuse this probe, it
now selects fixtures positionally (`ORDER BY created_at LIMIT 1`), fails with a clear message instead
of a `TypeError`, and carries the current baseline. No hardcoded demo names remain in it.

## 5. Regression gate

### The test fixtures were wrong in the same way the seed was

Moving DATE writes to UTC midnight invalidated every fixture that built one at *local* midnight —
`makeSprint` and `makeOnCallShift` in the shared factories, plus four suites' private copies of the
same helper. Those fixtures inserted a row one day earlier than the API read it back, so the
assertions failed. **The product was right and the fixtures were stale**, which is the outcome that
most deserves stating plainly: it would have been easy to "fix" the product back into the bug.

They are consolidated into `tests/test-utils/dates.ts` — one documented place to build a DATE fixture
— rather than six near-identical private helpers, because six copies drifting apart is what produced
this in the first place. On-call fixtures that must straddle "now" are keyed to `dhakaDayOffset`, the
same Dhaka calendar the product uses, so they cannot disagree with it for six hours every night.

**A seventh copy hid from the first sweep.** `tests/tasks/my-work.test.ts` wrote the same bug a
different way — `setHours(0, 0, 0, 0)` on a local `Date` rather than `new Date(y, m-1, d)` — so it
matched none of the patterns I had grepped for, and its three `Bucketing` failures survived into a
clean run. A task seeded as "due today" was stored as due *yesterday* and came back in the `overdue`
bucket.

The thing that told me this was the fixture and not the service: `fixing/evidence/F03/mywork-buckets.cjs`
drives the real API and puts all five buckets right, under both `TZ=Asia/Dhaka` and `TZ=UTC`. When a
unit test and an end-to-end probe disagree about the same behaviour, the one holding a hand-built
fixture is usually the one that is wrong — and searching for a *concept* ("a DATE built at local
midnight") rather than for the one spelling I had already seen would have caught it in the first
pass.

### Two constraints this phase ran into, worth recording for later phases

**Concurrent jest runs mass-fail under load.** Running a second suite alongside the sweep made all 81
on-call tests fail on a 5-second `resetTestDb()` *hook* timeout — no assertion involved. This is the
documented load-flake pattern and it is easy to misread as a real regression. **Run one jest
invocation at a time on this box**, and read a mass-failure at `setup-each.ts:22` as contention until
proven otherwise.

**A sweep that straddles an edit proves nothing about either version.** ts-jest compiles per file at
require time, so the long sweep's later modules loaded source that its earlier modules did not. The
`tasks` module in `jest-sweep.txt` (4 failed / 359) ran across the `ymd` split and is therefore
evidence about neither tree — the clean re-run in `tasks-clean.txt` supersedes it.

(The sweep happened to reach every *other* clock-affected module after the last edit had landed, so
only `tasks` actually needed re-running. `rerun-affected.sh` is kept as the general tool for the next
phase that needs it — pass module names as arguments — but F3 did not need to run it.)

The one failure I did capture from that run names itself clearly, and it is **not** a clock
regression:

```
● GET /api/v1/lists/:listId/tasks › Concurrency › serves 50 parallel reads with identical results
  Expected: 200
  Received: 500        tests/tasks/list-by-list.test.ts:1115
```

That is **ISS-087** (50 concurrent requests exhaust the connection-pool queue and return 500s),
already filed, already re-verified as reproducing in PHASE-42, and owned by a later phase. It is
load-sensitive, which is exactly why it surfaced while two jest runs were competing for the pool.
