## 1. ISS-058 — `workspaces.timezone` now decides "today"

**What was wrong.** The setting was stored, editable through `PATCH /workspace`, validated against
`Intl`, returned on the wire — and read by *nothing*. Every date boundary (`dueToday`/`overdue`
KPIs, the agenda's default date, all five My Work buckets) came from the API box's OS clock. F3 had
already moved My Work off the OS clock onto a named constant (`dhakaToday()`), which made the final
step small: replace the constant with the setting.

**The change.**

| file | change |
|---|---|
| `utils/dhakaTime.ts` | new `zoneDateOf(utc, zone)` / `todayInZone(zone)` — Intl-based (full ICU, DST-correct, no MySQL tz tables), falling back to the Dhaka calendar for a null/garbage zone |
| `TaskWriteService.myWork` | `today = todayInZone(workspace.timezone ?? "Asia/Dhaka")` |
| `HomeService` | same for the KPI day-keys + the agenda's default date (`zoneOf()` helper) |
| both services | gained a `WorkspaceRepo` constructor dep — wired at all five DI sites (`routes/tasks`, `engineering`, `forms`, `home`, `assistant`) |

The **company calendar** stays Dhaka on purpose: dept-review weeks (D-3 spec: Dhaka Mon–Sun) and the
on-call roster still use the fixed-offset `dhakaToday()`. Those are company-wide artifacts; the
workspace setting governs what an individual's "today" means. The boundary is documented in
`dhakaTime.ts` itself.

**Proof — deterministic at any wall-clock moment** (`f5-timezone.txt`, exit 0). Pacific/Kiritimati
(UTC+14) and Pacific/Midway (UTC−11) are 25 h apart, so at every instant at least one of them is on
a different calendar day than Dhaka. For each of the three zones, a task due that zone's *own* today
/ yesterday / +3d landed in `today` / `overdue` / `next`, the `dueToday` and `overdue` KPIs rose by
exactly one each (delta-based — the demo seed already has owner-assigned due tasks), and the
no-param agenda served that zone's today. Then the sentence itself:

```
under Asia/Dhaka       the task due 2026-08-04 is `today`,  on today's agenda
re-zone to Pacific/Midway (only the timezone changes)
under Pacific/Midway   the SAME task is `next`,  and it has LEFT the agenda
```

Changing the workspace timezone now changes what "due today" means — the issue's Expected line,
verbatim.

## 2. ISS-063 (client half) — an edited comment now says so

**What was wrong.** The API set `edited_at` and returned it; a grep across the whole client found it
only in two type declarations. `CommentsSection` showed author, body, time — a comment could be
rewritten inside its 15-minute window (real since F3) with nothing shown to readers. This is the
accountability surface the window exists for.

**The change.** `client/src/components/task/CommentsSection.tsx` — an "(edited)" marker after the
timestamp, italic, muted, with the full instant in the hover title
(`Edited 8/4/2026, 12:08:14 PM`). Guarded `editedAt && !deletedAt` so a deleted tombstone stays
bare. The axios layer's R1 rule already camelises `edited_at` → `editedAt`, so no mapper work.

**Proof, both halves:**
- *Wire* (`f5-edited-wire.txt`, exit 0): fresh comment → `edited_at: null`; PATCH inside the window
  → set; the **list read the drawer renders from** carries it; a deleted comment carries
  `deleted_at` (so the guard does real work).
- *DOM* (`edited-marker.png` + the spec): a real browser session — login, open the task drawer via
  `?task=<id>` — shows **exactly one** "(edited)" marker, on the edited comment and not its
  untouched neighbour, with the `Edited …` title attribute. The spec is permanent coverage:
  `client/e2e/f5-edited-marker.pw.ts`, self-contained (builds its fixture through the API, cleans
  up, no hardcoded ids — unlike the older specs it sits next to).

**Deliberately not done:** the plan's optional hardening (move the window check into SQL) — F5 never
touched `CommentsService`, and the JS comparison is correct now that both clocks agree. Noted, not
done, per the plan's own "only if touching that file anyway".

## 3. The boot-time clock guard

`db/client.ts` — production now **refuses to start** unless `DB_TIMEZONE=+00:00`:

```
prod       + +00:00   BOOTED
prod       + +06:00   REFUSED   "Refusing to start: NODE_ENV=prod requires DB_TIMEZONE=+00:00 …"
prod       + unset    REFUSED
production + +06:00   REFUSED   (the gap-scan M4 spelling alias, via Config.IS_PROD)
dev        + anything BOOTED    (dev is not guarded — its .env carries the canonical value)
```

(`boot-guard.txt` — the guard runs at module load, before any connection.) The process `TZ` is
deliberately **not** checked: F3 decoupled it (pm2 keeps `TZ=Asia/Dhaka` while the session is UTC),
so the guard is on the value that matters, not on an agreement between files. This closes ISS-058's
"production coupling" half: the failure mode it described — a systemd unit or container starting the
API with the wrong clock — now fails loudly at boot instead of silently corrupting every timestamp.

## 4. Observations (recorded, not fixed — rule X1)

- **`users.timezone` is still read by nothing.** ISS-058 names it, but the plan's F5 scope (and the
  issue's own Expected line) is the workspace setting; per-user zoning is a product decision about
  *whose* calendar wins and belongs with the F28 decision batch if wanted. ISS-058's status note
  says so explicitly.
- **Sparkline day-keys have a cosmetic residual.** The 7-day histograms bucket by SQL
  `DATE(created_at)` (a UTC day since F3) while the day *labels* are workspace-zone days; a task
  created 00:00–06:00 Dhaka lands one cell off. Totals (`value`) are unaffected — the KPI *numbers*
  are right. Fixing it needs `CONVERT_TZ` with named zones (MySQL tz tables — not loaded on the dev
  box) for DST zones. Out of proportion for a histogram cell; recorded here.
