## 1. ISS-089 — the API bound every interface

`app.listen(PORT, …)` with no host argument binds `::`/`0.0.0.0`. With `trust proxy = 1`, Express
takes `req.ip` from the **last** `X-Forwarded-For` entry — and a client talking straight to the API
is the only hop, so it controls that value completely. P41 measured the result:

```
6 bad logins from one client              -> attempt 6 = 429, Retry-After 60     correct
the same, with X-Forwarded-For: 1.2.3.4   -> 401 every time    *** fresh bucket per request ***
```

The login limiter is the only thing standing between a public hostname and offline-quality password
guessing, and one header defeated it.

**The change.** Production binds **127.0.0.1**. nginx already proxies to `127.0.0.1:5501`, so nothing
legitimate changes. **Dev keeps the wildcard on purpose**: the CORS policy deliberately reflects
private-LAN origins so a phone on the same Wi-Fi can use the app, and that is pointless if the port
itself is unreachable.

**Proof — booted, not asserted from source** (`bind-proof.txt`):

```
dev  (NODE_ENV=dev,  :5721)   listening on ::           <- wildcard, unchanged
prod (NODE_ENV=prod, :5722)   listening on 127.0.0.1    <- loopback only
                              "Listening on 127.0.0.1:5722 (loopback only)"
```

> The issue asks to **first confirm whether TCP 5501 is firewalled on 209.38.65.61**, because that
> decides whether this was ever exploitable. That check needs the production box and has not been
> run — it is a one-line `ufw status` / external `nc` for the operator. The fix is correct either
> way (defence in depth costs nothing here), but the *severity* of what came before is still open.
> Carried in the issue's status note rather than quietly dropped.

## 2. ISS-085 / ISS-009 — a rejected Origin was a 500

`cb(new Error("Origin … not allowed by CORS"))` makes the `cors` middleware **throw**, which reaches
the global handler as an unknown error. Every disallowed origin produced a 500 *and* an
`Unhandled error` log line — five origins, five phantom server faults. The policy was already right
(P2 verified all 10 cases including the prefix and fragment tricks); only the reporting was wrong.

`cb(null, false)` instead: no `Access-Control-Allow-Origin` header, so the browser blocks the read —
which is the intended outcome — and the request is answered normally.

```
                              before          after
https://evil.example.com      500 + log       401, no ACAO
null                          500 + log       401, no ACAO
http://localhost.evil.com     500 + log       401, no ACAO
OPTIONS preflight from evil   500             200, no ACAO
http://localhost:5173         200 + ACAO      200 + ACAO   (unchanged)
legitimate preflight          204             204          (unchanged)
```

(The 401 is the endpoint answering an unauthenticated request — exactly what a same-origin caller
would get. The CORS layer no longer has an opinion beyond the missing header.)

## 3. ISS-086 — headers

`x-powered-by: Express` is gone (`app.disable`). A CSP now ships, and for a JSON API the honest one
is **`default-src 'none'`** — this origin serves no HTML, scripts or styles, so if an XSS ever lands
in a JSON error string there is nothing for it to reach. Plus `frame-ancestors 'none'`,
`base-uri 'none'`, `form-action 'none'`, `Cross-Origin-Opener-Policy: same-origin`,
`Cross-Origin-Resource-Policy: same-site`, `X-DNS-Prefetch-Control: off`.

The **SPA origin needs a different, much looser policy** — it is a separate nginx-served origin and
not this middleware's job; the issue says the same. HSTS is unchanged: prod-only, because
advertising it from plain-HTTP localhost poisons the browser's HSTS cache for every dev.

## 4. ISS-091 — `/health` through nginx, and `/metrics` denied on purpose

The vhost proxied only `/api/v1/`, but `/health`, `/health/ready`, `/health/version` and `/metrics`
are mounted at the **app root**. They fell into the SPA catch-all, so
`https://tasks.beautybooth.com.bd/health` returned **index.html with a 200** — an uptime monitor
watching that URL would report "up" for a dead API, which is worse than no monitor at all.

- `location = /health` now proxies. Exact match: the liveness probe reveals nothing but that the
  process answers. `/health/ready` and `/health/version` stay unproxied on purpose — `ready`
  exposes DB reachability and `version` the running build.
- `location /metrics { deny all; }`. It was already unreachable, but only **accidentally** — it fell
  through to the catch-all. Protection by coincidence is not protection; the next person to add a
  location could remove it without noticing.

The stale comment in the catch-all that claimed those paths were protected by the fallback was
corrected in the same edit — it would now be actively misleading.

> `nginx -t` is a **deploy-box step and has not been run**: nginx is not installed on this Windows
> dev machine. The change is two locations in the same style as the four already there, but it must
> be `nginx -t`'d before reload. Flagged in the issue's status note.
