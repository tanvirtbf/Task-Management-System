**Status:** DONE
**Fixes:** ISS-083 (HIGH — the policy was length-only) · ISS-030 (a member could move their own
login email anywhere, silently) · ISS-031 (a bogus IANA zone was accepted on a user profile)
**Risk taken:** 🟢 — three validation/authorisation narrowings; no schema, no data
**Gate:** `auth` **339/339** · `users` **282/282** (279 + 3 new specs) · `health` 14/14
**Data left behind:** none — throwaway accounts only, baseline re-verified

## 1. ISS-083 — the password policy

**What was wrong.** The entire rule for a new password was `isLength({min:8, max:200})`. P38 measured
the consequence: `password`, `12345678`, `PASSWORD`, `aaaaaaaa` and `alllowercase` were all
**accepted with a 204**. Only a 5-character string was refused, and only for length. Three
endpoints each carried their own copy of that one rule, which is how a policy drifts.

**The change.** One shared module, `validators/passwordPolicy.ts`, used by all three
(reset-password, change-password, accept-invitation). It refuses, in this order:

| rule | catches |
|---|---|
| length 8–200, counted in **code points** | `short7!` |
| the same character repeated | `aaaaaaaa`, `11111111` |
| a straight run off the alphabet or keyboard | `12345678`, `abcdefgh`, `qwerty` |
| a common-password denylist, matched on a normalised form (lowercased, and again with trailing digits/punctuation stripped) | `password`, `Password1!`, `password123`, `beautybooth` |
| at least 3 of {lower, upper, digit, other} | `alllowercase`, `PASSWORD` |

**Why it is shaped this way, and what it deliberately does NOT do.** NIST SP 800-63B's modern
guidance is that a blocklist does far more good than composition rules, and that mandating symbols
mostly produces `Password1!` — so the denylist is the primary rule and composition is the backstop.
Two escape hatches follow from that:

- **A 16+ character passphrase skips the class rule.** `correct horse battery staple` is stronger
  than `Abcd123!`; refusing it would teach people to write shorter, worse passwords.
- **A non-ASCII password skips it too.** *This one was a real defect in my first cut, and the repo's
  own test caught it.* The class check was written with `[a-z]/[A-Z]/\d`, so
  `পাসওয়ার্ড🔥1` — Bangla plus an emoji, strong by any measure — was **refused**, while `Abcd123!`
  passed. In a Bangladeshi company that is not a rounding error: it quietly pushes people off their
  own script and onto weaker ASCII. `reset-password.test.ts` → *"handles a unicode password (emoji +
  Bangla) end to end"* went red, and it was right. Non-ASCII now exempts the class rule for the same
  reason length does — such a password is on no wordlist and no keyboard walk.

**The minimum stayed at 8.** Raising it was considered and rejected: it would have been a bigger
behaviour change than the defect warrants (~24 existing fixtures sit at 9–10 characters), and the
rules above already refuse every example ISS-083 recorded. `bcrypt` cost 10 and the no-trim rule are
unchanged — P38 verified both as correct and neither was touched.

**Proof.** `policy-cases.txt` — a 24-row decision table, run against the module directly: ISS-083's
five, seven more of the same class, and twelve that must NOT be refused (including every fixture the
3,500-test suite depends on, and the seeded `Owner@12345`). **24/24 correct.** Then end-to-end on a
throwaway account, all three endpoints: `f12-probe.txt`.

> P38's own warning was respected. The probe that found this issue changed the **owner's real
> password** to `alllowercase`. This one creates and deletes its own accounts and never touches a
> seeded credential.

## 2. ISS-030 — the login email is now admin-only

**What was wrong.** `PATCH /users/:id {"email": …}` on your own account: **200, written**. No
verification, no notification to either address. Three consequences, and the second is not
hypothetical:

1. The change is silent — the original holder is never told.
2. It **frees the corporate address**, so a later invite to it creates a *brand-new, different*
   account. This happened by accident during P7 and the two records had to be untangled by hand.
3. With forgot-password it is a **persistence primitive**: a minute at an unlocked laptop (ordinary
   in a 100-person office) moves the account to an attacker's mailbox and survives every later
   password reset.

**The change.** `UserService.updateProfile` — a non-admin changing the email is
`403 user.email_change_forbidden`. The issue's own Expected line offers two acceptable outcomes:
verify the new address, or make it admin-only. Admin-only is what ships: no schema column, no mail
round-trip, and these are corporate addresses created by invite, so self-service email change was
never a needed capability. A **same-value echo is still allowed**, so an ordinary profile PATCH that
happens to include the current address does not start failing.

Everything else about the endpoint is unchanged — `role`, `status`, `id` and `password` were already
refused, and a member still edits their own name, timezone and avatar.

## 3. ISS-031 — a timezone that no date library can resolve

`PATCH /workspace` has always checked the value against the IANA list; `PATCH /users/:id` checked
only that it was a string, so `Not/AZone` was stored. `users.timezone` is on the wire in
`GET /users` and `/auth/me`, so any client doing `Intl.DateTimeFormat(…, {timeZone})` threw a
`RangeError` on that row. The user validator now uses **the same** `isIanaTimezone` — exported and
imported, not copied, since a second copy is how the two drifted apart in the first place.

## 4. Two tests asserted the old behaviour, and were updated with the reason

Both failures in the first gate run were specs pinning the vulnerability itself:

- *"lowercases a changed email before storing"* did it as a **member on themselves** — ISS-030's
  exact repro. Rewritten to exercise the lowercasing through an admin, plus two new specs: a member
  changing their own email is 403, and a same-value echo still passes.
- *"accepts a timezone at exactly the 64-char boundary"* asserted `"a".repeat(64)` was accepted. The
  column is `VARCHAR(64)`, so length was the only rule — that IS ISS-031. The IANA rule is strictly
  narrower (the longest real zone is ~32 characters), so **the 64-char boundary is now unreachable
  by design**. Replaced with: a 64-char non-zone is refused, and a long real zone is accepted.

`users` therefore goes 279 → **282**.

## 5. D5 — decided, and why it did not need to be asked

The plan flags a decision: *does the new rule apply to existing users at next login, or only to new
passwords?* **New passwords only** — no forced reset. D1 already established production is not live,
so the "~100 accounts on one shared password" the decision was written about do not exist yet; the
only accounts are 15 seeded demo users. Forcing a reset would need a schema column
(`password_changed_at` or a `must_change` flag) and a login-flow change, for a population of zero.
The seeded credential `Owner@12345` satisfies the new policy anyway.

**This is reversible and belongs to the user.** If real accounts are created on weak passwords
before go-live, a forced rotation is a separate, small piece of work. Recorded in
`fixing/DECISIONS.md` as chosen-by-default rather than answered.
